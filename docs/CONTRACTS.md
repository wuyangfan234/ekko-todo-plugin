# Ekko ToDo Data Contracts & Persistence

Authoritative field schemas live in `contracts/plugin.json`. This document summarizes runtime storage, lifecycle guarantees, and host boundaries.

## Storage & Isolation

- All durable state is stored in `ekko-todo.sqlite` inside the host-managed `ctx.paths.dataDir` (retained across plugin upgrades and reloads; never inside the package install directory).
- SQLite runs in `WAL` mode with `foreign_keys = ON` and `busy_timeout = 5000`.
- Every entity (`projects`, `agents`, `config_cooldowns`, `memories`, `topics`, `topic_messages`, `topic_queue`, `todo_queue`, `todos`, `todo_counters`, `todo_watches`, `schedules`, `quota_providers`, `settings`) is strictly scoped by `(user_id, profile)` derived from `run.identity` (never trusted from browser input).
- Isolated Git worktrees are created under `<dataDir>/worktrees/`, keeping the user's main repository checkout clean at all times. Project Workspace file/branch/history browsing uses pure read-only Git object commands (`git for-each-ref`, `git ls-tree`, `git show`, `git log`) with zero checkout or working-tree mutations.
- Scheduled task runs (`schedules`, max 50 per profile) evaluate wall-clock timezones via `Intl.DateTimeFormat`, never backfill missed cycles, skip closed/unassigned todos with recorded reasons, override stale runs on next tick, and can be managed by both UI and Chief MCP tools (`list_schedules`, `create_schedule`, `update_schedule`, `delete_schedule`).
- Quota & Token Hub credentials (`quota_providers.secret_value`) are stored server-side only and strictly masked (`hasSecret`, `secretPreview`) in every client snapshot; independent per-provider detection runs natively inside Ekko ToDo via official vendor APIs and built-in local credential/client discovery (Kimi Code, Grok, DeepSeek, Antigravity local language server, Codex, Claude, OpenRouter, Custom balance APIs) with zero dependency on external CodexBar CLI or Magpie. Native token usage records persist in `usage_records`.

## State Machine, Model Failover, Memories & Idempotent Wakes

- Todo lifecycle transitions (`todo`, `queued`, `confirm`, `building`, `reviewing`, `merging`, `review`, `failed`, `done`, `closed`) are validated by an XState v5 statechart (`src/server/state-machine.mjs`). When concurrency slots are full, new builds enter `queued` and automatically start via `drainQueuedTodos()` when a slot frees.
- Chief strict orchestration (`settings.chiefStrictOrchestration`, default `true`) physically isolates Chief sessions in `<dataDir>/chief-workspace`, provides read-only `inspect_project_repo` (MCP tool #27), monitors direct mutating tool calls, and audits registered project repo fingerprints pre/post-turn.
- `todo-action` `delete` removes a card on user request: it refuses while `merging`, stops live build/review sessions, removes the plugin worktree, deletes the task branch only when already merged (`git branch -d`, unmerged branches stay), and drops its watches, wake log and schedules. Todo numbers come from `todo_counters` (per-project high-water mark) and are never reused, so a new card can never pick up an old branch.
- Mid-run Chief messages and automated task wakes arriving while Chief is busy are persisted in `topic_queue` and drained in strict FIFO order (coalescing consecutive wakes) so turns never collide and multi-todo wakes are never lost.
- Isolated Git worktrees auto-symlink gitignored dependency paths (`.venv`, `node_modules`, `.env`) for out-of-the-box test execution and safely unlink recorded symlinks before worktree removal. Two passes (since 0.9.71, #94), both through the same record / `.git/info/exclude` / manifest step: (1) the static candidate list (`src/server/git-engine.mjs` `WORKTREE_BOOTSTRAP_CANDIDATES`, now including `backend/engines/node/node_modules`); (2) a bounded auto-discovery of the main repository: real directories named `node_modules`, `.venv` or `venv` at depth 1-4 below the repository root (`backend/engines/node/node_modules` is depth 4), never entering `.git`, a found dependency directory or a symlink, reading at most 4000 directories, deduplicated against the static list, and linking at most 12 paths (shallowest first, then by name). A discovered path is linked only when `git check-ignore` (which consults the index, so tracked paths never match) reports it ignored, `git ls-files` lists nothing under it, its parent directory already exists in the worktree and the worktree path does not exist yet. Any discovery error just means fewer links; worktree creation never fails because of it. Safety boundary unchanged: cleanup removes only symlinks recorded in the manifest (`.wt-links-<worktree>.json`) and never the main repository's directories; tracked directories are never linked; the worktree tree snapshot excludes recorded links. A second bootstrap of a reused worktree now keeps earlier entries in the manifest instead of overwriting them. No new contract key, RPC, tool or table.
- Worktree capture first bounds previews to 20 files, 180 lines per file, 2,000 characters per line, 20,000 characters per file, and 200,000 UTF-8 bytes for the serialized `diffs` array. The original character count survives the subsequent shared clamp, and budget-exhausted tail entries retain minimal `path`/`additions`/`deletions` statistics. These capture bounds feed, rather than replace, the v0.9.8 `clampDiffs` and `fitSnapshotBudget` protections below.
- Each Agent stores up to 8 ordered `modelConfigs` (primary + fallbacks), an `autoFallback` toggle, and a `maxTurns` budget (`0` = unlimited, or explicit `1–2000`; stored clamped). Default since 0.9.70 (#92): `500` for an Agent created without `maxTurns` — the editor draft, RPC `save-agent` / MCP `configure_agent` with the field omitted, the preset chief / builder / reviewer and team-preset workers; column default `500` in both `CREATE TABLE` and the `ensureColumn` migration. This is the plugin's own default only: the host (`~/.hermes/config.yaml`, `agent.max_turns`, `HERMES_BRIDGE_MAX_TURNS`) is never read for it nor written. Existing Agents are not migrated: a stored value — including an explicit `0` ("不限", chosen by the user) — is kept as is; updating an Agent without `maxTurns` keeps its stored value. Before 0.9.70 the default was `0`. Since 0.9.70 (#84) it is always sent as the `sessions.run` option `max_turns` — `0` included, because Hermes `resolve_turn_limit` reads `0` as unlimited (previously `0` omitted the option, which silently meant "inherit the host cap", 150 on a fresh install). Hermes Web UI 0.8.31 does not forward `max_turns`: every plugin session runs with the bridge cap `HERMES_BRIDGE_MAX_TURNS` (> 0) or a positive `~/.hermes/config.yaml` `agent.max_turns`, else `90` (a `0` there is read as 90, not unlimited). The snapshot reports that enforced cap as `runtime.hostTurnBudget` `{ effective, source: env|config|bridge-default, configured? }` (`configured` omitted when config.yaml has no `agent.max_turns`) and the Agent editor shows it with how to change it. On genuine model/provider service faults (quota, 429/529, 401/403, 5xx, network timeout, incompatible parameters, and since 0.9.46 an empty model response), `src/server/failover.mjs` records a 1-hour cooldown in `config_cooldowns` and automatically reruns on the next healthy fallback configuration.
- Failure categories (`classifyModelFailure`, stored in `todos.fallbackHistory[].category` and `config_cooldowns.category`). Not switchable: `non_model` (abort / cancel / stopped by user, merge conflict, uncommitted changes, worktree, test gate, `rc=1…9`, and since 0.9.46 the bare fallback wording `执行会话异常结束` / `审查会话异常结束`; checked first, so such a text never switches even when it also names a model fault) and `unknown` (empty text, or nothing matched). Switchable: `quota_spent`, `rate_limited`, `auth_failed`, `model_unavailable`, `upstream_fault`, `network_cutoff`, `incompatible_request`, and since 0.9.46 `empty_output` (label `模型返回空响应`: `response.output is empty`, `empty after stream backfill`, `Invalid API response`, `no content`, `no visible content`, `empty response`, `empty output|message|completion`, `Reasoning-only response`, `无输出`, `空响应`). The first two `empty_output` wordings are checked before the other switchable categories, the rest after them, so `Invalid API response …: 429` stays `rate_limited`. No stored value is migrated; rows written before 0.9.46 keep their category.
- Failed build run (since 0.9.46). The cause is the `error` / `message` of the host `chat.run.failed` event (a string, or an object with `message` / `error` / `detail`). When that is empty or only `执行会话异常结束`: (1) an event with `interrupted: true` is recorded as `运行被中断，宿主没有给出错误信息（会话 <id>…）`, category `non_model`; (2) otherwise `host.sessions.get(sessionId)` is read for at most 3 s and the first non-empty of `lastError`, `last_error`, `error`, `errorMessage`, `error_message`, `failureReason`, `failure_reason` (on `session`, then on the answer itself) is the cause; (3) otherwise, when the transcript was read, is not empty and holds no assistant text after its last user message, the cause is an empty model response (`empty_output`, switchable); (4) otherwise the category is `unknown` and the text is `未能取到模型侧原始错误（会话 <id>，配置 <config label>，宿主事件 code=… stop_reason=…）` (the last part only when the event carried `code` or `stop_reason`, each cut to 80 characters). `todos.lastError` is the cause cut to 400 characters plus `…`, prefixed `模型服务异常（<category label>）：` when the category is switchable and left as is otherwise; the timeline gets `构建失败：<lastError>`. A switchable fault with `autoFallback` on and no config to switch to (none configured, or all inside the cooldown) additionally writes the timeline line `模型 <config label> 服务异常（<category label>），但没有可用备选配置…` (actor `failover`) and the card fails. The wording of a failed review run (`审查会话异常结束`) and of a failed Chief run (`总管会话异常中断`) without an event error is unchanged.
- Idle build round (since 0.9.47). `todos.evidence` (a JSON object, shallow-merged on every write; no column and no migration) gains four optional keys. `roundBaseSha` (string, full sha, default `''`) and `roundBaseTree` (string, tree sha, default `''`) are written by every build dispatch: HEAD of the worktree and the tree of its files on disk (uncommitted and untracked included, bootstrap symlinks excluded) at that moment; both are `''` when they could not be read after two attempts (timeline `本轮无法确定基线，跳过产出校验`), and an instruction the host refused as "already running" leaves the values of the running turn in place. `gateSkipped` (string: `''`, `'no-new-commit'` or `'no-snapshot'`) is reset to `''` by every dispatch, which also resets `testRc` to `-1` and `testSummary` to `''` (the result of the round before is not shown while the next round is building). `idleRetries` (integer, absent = 0) counts the automatic reruns of the card after an idle round and is never reset. When a build turn ends as completed, before the test gate: the snapshot's `headSha` and `worktreeTreeSha` (both new in the result of `captureWorktreeSnapshot`) are compared with the baseline. Both equal = idle round. A moved HEAD (an empty commit, or a commit that is reverted by a later commit, included) or a changed tree (uncommitted edits included) = output, and the settle is what it was before. Not judged: planning rounds (`withPlan`; nothing is written), a missing snapshot (the worktree is gone or the snapshot failed; timeline `取不到工作树快照，跳过产出校验`; when the project has a test command it is not run, `evidence` gets `gateSkipped: 'no-snapshot'`, `testRc: -1`, `testSummary: ''`, and the card reaches the review gate with `gateOwner: 'human'`), a missing baseline, e.g. a card dispatched before 0.9.47 (timeline `本轮没有可用的开工基线，跳过产出校验`). `kind: 'deploy'` cards are judged like any other card. A round that ended with the host event `chat.run.stopped` (the settle input `stopped`, default `false`) is compared too: with output it settles as before; without output it is never rerun, the card goes to `failed` with `lastError` `本轮被停止，没有产出（HEAD 仍为 <12-char sha>）` (plus `，未提交的改动与开工时相同` inside the brackets when the files on disk differ from HEAD), `gateSkipped: 'no-new-commit'`, no `config_cooldowns` row, no `fallbackHistory` entry, `idleRetries` unchanged, and the Chief is not woken. An idle round never runs the test gate. With `autoFallback` on, `idleRetries` below 1 and a config to switch to, the card stays `building` and is dispatched again in a new session on that config: `idleRetries` + 1, a `fallbackHistory` entry and a `config_cooldowns` row with category `idle_build` (label `构建会话空转（无产出）`; this value is produced by the orchestrator only, `classifyModelFailure` never returns it). The `config_cooldowns` row is written only when the card really switches: with nothing to switch to, the config that idled is not cooled down. When the rerun cannot be started the card goes to `failed`, `lastError` is the idle text plus `；自动重跑未能启动：<reason, at most 300 characters>`, and `idleRetries` is set back to its value before the attempt (the `fallbackHistory` entry and the cooldown stay). Otherwise the card goes to `failed` (`gateKind: 'failed'`, `gateOwner: 'human'`), `lastError` is `本轮没有产生任何提交（HEAD 仍为 <12-char sha>），任务未推进`, or `有改动未提交，且 HEAD 未前进（<12-char sha>）` when the files on disk differ from HEAD, and `evidence` gets `gateSkipped: 'no-new-commit'`, `testRc: -1`, `testSummary: ''` (a result left by an earlier round is cleared, so the Chief merge gate cannot read it as passing).
- Idle governance (#105, audit #95 P1-5 / P1-6). Additive only: no RPC, tool or model shape changes except one optional settings field; stored data is not migrated and no version is bumped.
  - Worker idle count. `todos.evidence.idleNudges` (integer, absent = 0; already persisted on the card, so a reload keeps it) counts the automatic "keep going" nudges of the current idle chain (at most 3, then the card fails or is rerun as before). Before #105 every dispatch without the nudge flag reset it (a manual `run_build`, a queued instruction delivered after a turn, the idle rerun on a fallback config), so a card could idle 8+ rounds without being caught. Now no dispatch, message, queued instruction or nudge resets it. It goes back to 0 only (a) after a productive round — the round reaches the plan gate (`PLAN_READY`) or the build gate (`BUILD_COMPLETED`: a moved HEAD or a changed tree, or no baseline to compare), or is settled as a deliverable / an evidence report / a merged-branch answer (`settleTextDeliverable`); timeline `本轮有产出，空转计数（<n>/3）清零` — or (b) when the chain ends: the card fails as idle (`settleIdleBuild` without a rerun, or a planning round without a plan); timeline `空转计数已到期（<n>/3），本链结束，计数清零`. Both lines (actor `orchestrator`) are written only when the count was above 0. A failed run (model error) is not output: the count stays. The idle rerun on another config therefore starts with the count it had (usually 3): it gets no fresh nudges, and an idle rerun fails at once.
  - Chief idle rounds. New additive column `topics.chief_idle_json TEXT NOT NULL DEFAULT '{}'`, written only by `db.setTopicChiefIdle`; the topic record carries the read-only view `chiefIdle: { count, resumes, exhaustedNoticed, updatedAt }` (integers 0–1000, boolean, ms; `'{}'` and unreadable JSON read as all zero). After every completed Chief turn (except the "Ekko ToDo tools not loaded" case) the round is classified by `classifyChiefRound` (`src/shared/chief-guard.mjs`) from the host transcript tail (60 rows; a round whose user message is not in view is neutral):
    - productive: a dispatch tool was called (`classifyChiefToolCall` category `dispatch`, also through `tool_call`), or the final reply carries a verifiable conclusion (`hasVerifiableConclusion`: a card number with a final or explicit state (`已完成` / `已合并` / `合并至` / `已通过` / `失败` / `已关闭` / `已取消` / `已打回` / `已进入构建|审查`, `phase=…`; not `待` / `进行` / `阶段`), a `file:line` reference (a bare path is not one), a 7–40 hex sha that stands alone (not inside `proj-…` / `agent-…` ids) with `commit` / `提交` / `HEAD` / `合并` / `sha` next to it, `rc=` / exit code, a test result (`pass N` / `fail N` / `N passed`, or N 用例/测试 with 通过/失败/全过), or a code block. Counts such as `3 个工具` or `5 分钟` are not conclusions; in a reply of ≤ 120 chars a sentence that announces the next step (`我先` / `我去` / `让我` / `I will` …) never counts, whatever it mentions; the other sentences of that reply are judged normally, `我先看了…` / `我去跑了…` (了 / 过 / 完 in the clause) is a report and not an announcement, and a short announcing reply that contains a code block does not count at all). An intent sentence is not a conclusion (意图句不算结论): tense is judged before the identifier. Sentences end at `。！？!?；;`, a line break, or an English full stop followed by whitespace or the end of the text (the dots in `src/a.mjs` or `0.9.71` do not end one); clauses are cut at `，,`. A hit other than a code block does not count when one of three kinds of marker is in reach: (1) the speaker's own plan or a condition, in the hit's clause or the clause right before / after it — `我会` / `我再` / `我将` / `准备` / `打算` / `稍后` / `接下来` / `下一步`, `我先` / `我去` without 了 / 过 / 完, `之前|以前` + `我|先|再|要`, `…后再|才`, `先…再`, `再核|查|跑…`, `才能`, `需要…后`, `如果` / `一旦`, `will` / `going to` / `if` / `once …` / `before I|merging …`; (2) waiting on something, in the hit's clause or the clause before it — `等…`, `等待`, `待验证|执行…`; waiting on the user (`等你` / `等用户` / `等确认` / `等拍板`, `等待合并|确认|验收`) is never a marker and a wait after the result does not void it; (3) a guess, in the hit's own clause only — `应该` / `应当` / `预计` / `should`. So `合并 deadbeef 之前我再确认`, `准备去跑 npm test 拿 rc=0`, `应该会是 rc=0`, `我会把 #12 已合并的情况再核一遍` and `#12 已合并，我再去派 #13` are not conclusions, while `跑完 rc=0`, `我先看了日志，问题在 src/a.mjs:12`, `根因确认在 src/a.mjs:12，应该改成 x`, `#12 审查通过，等待合并`, `Merged #12 (commit abc1234). Next I will dispatch #13.` and `#12 已合并至 main` followed by `下一步：派 #13` on the next line are. This is fail-closed and has a real cost: a result with the speaker's plan in the neighbouring clause of the same sentence (`#97 已合并至 main，我再去派 #98`) is not counted, every such round after read-only probing adds 1 to `count`, and a Chief that habitually reports as "result, then plan" in one sentence reaches the hint at 3 and the breaker at 4 although it did report results. Writing the result and the plan as separate sentences or lines avoids it. `count`, `resumes` and `exhaustedNoticed` go back to 0 / false; when `count` was above 0 the topic gets `总管本轮有产出（…），空转计数（<n>）清零`.
    - idle: announce-only (as 0.9.62), or every tool call of the round is read-only / probing — `tool_search`, `tool_describe`, `read_file`, `search_files`, `list_*`, `inspect_*`, `get_*` (MCP prefixes and the host `_u` spelling seen through; a `tool_call` wrapper counts only when every inner tool does) — and the reply has no verifiable conclusion (an empty reply included). `count` + 1. At `CHIEF_IDLE_HINT_AT` = 3 the topic gets `提示：总管已连续 3 轮没有产出（…）。再空转 1 轮将熔断：不再自动续跑。`; at `CHIEF_IDLE_BREAK_AT` = 4 the breaker trips: the topic gets once `已熔断：总管连续 4 轮没有产出（…），已停止本轮、不再自动续跑。建议：…` (three concrete actions), and from then on no automatic resume is queued after an idle round until a productive round resets the count. The round itself had already ended; nothing else is stopped and wakes from cards are still delivered.
    - neutral: a question to the user, a plain answer without tools, a round with other tools (memory, plans, clarify, a flagged write / execute call). Nothing changes.
    - A user message re-arms `resumes` and `exhaustedNoticed` but never resets `count`. `DESCRIBE_ONLY_LIMIT` (5 schema reads in a row inside one turn stops it) is unchanged and still applies; it is no longer the only protection.
  - Automatic resumes. An idle round below the breaker is resumed as before (0.9.62 / 0.9.64: at most `CHIEF_MAX_ANNOUNCE_NUDGES` = 2 per user message); a read-only round gets its own wake text (`formatChiefReadOnlyNudge`: give a verifiable conclusion or dispatch). The budget is now `chiefIdle.resumes` in the topic row instead of an in-memory map, so a reload does not hand out a fresh budget. When it is used up and the round is still idle, once per chain (`exhaustedNoticed`) the topic gets `本链续跑次数已用尽，需要人工介入：总管本链已自动续跑 <n> 次仍没有产出，不再续跑（关联任务 #<N>）。…` (with `todoId` of the card) and that card's timeline gets the same line plus `（话题「<title>」）`. The card is the one named by the newest topic message that carries a `todoId` (the progress notice that woke the Chief); without one only the topic line is written.
  - Chief gate reminder. New settings column `settings.chief_gate_stale_ms INTEGER NOT NULL DEFAULT 1200000` and `saveSettingsInput.chiefGateStaleMs` (integer ms; `0` = off, other values clamped to 300,000–86,400,000; default 1,200,000 = 20 min; snapshot `settings.chiefGateStaleMs`). Each `reconcileActiveRuns` pass looks at cards with `gateOwner: 'chief'` in phase `review` or `confirm` (`db.listChiefGateTodos`). A card whose `updatedAt` is older than the threshold on the orchestrator's `clock()` gets one timeline line and one topic message `关口提醒：#<N>「<title>」在总管关口（<phase>/<gateKind>）已停留约 <m> 分钟，没有被处理。…本提醒只写一次。` (actor `orchestrator`; the topic message carries the card's `todoId`; archived topics get none). `evidence.chiefGateRemindedKey` (string, absent = `''`) is set to `<phase>:<gateKind>:<snapshotSha>`: the same gate is never reminded again, a new gate (another phase, gate kind or snapshot) can be. The Chief is not woken and nothing is queued.
- Delivery and completion guard (#104, audit #95 P1-3 / P1-4 / P0-3). No column, no migration, no new RPC, tool, event or `evidence` key, no version bump; stored cards and watches are read as before. What changes is which calls are accepted and what a round's reply counts as.
  - **Completion guard** (`completeTodo`: RPC `todo-action` action `complete`, tool `complete_todo`). Checked on the server before anything is written; a refusal changes nothing on the card (phase, gate, branch, worktree, watches, timeline).
    - A card that waits for the user (`question.active`, or phase `confirm`) is refused: `#N 正在等待用户答复提问，不能直接标记完成…` / `#N 的方案正在等待用户确认，不能直接标记完成…`. Before, phase `confirm` answered with the state machine's English error.
    - A code card — kind `feature`, `bug` or `deploy`, with a `branch` or a `snapshotSha` — in phase `review` (the review, merge, deploy and deliverable gates) is refused with `#N 有未合并改动，请走合并或先取消（<原因>）。本次标记完成没有执行。` unless nothing of it is left outside the project's default branch: the worktree has no uncommitted entries (`git status --porcelain`), and `snapshotSha`, the tip of `refs/heads/<branch>` and the worktree HEAD (those that exist) are each an ancestor of the default branch (`git merge-base --is-ancestor`, the proof #102 asks of a merge). `<原因>` names the first failing check (`提交 <12 位> 不在 <默认分支> 中`, `工作树有 K 项未提交改动`, `读不到项目仓库…`, `读不到任务分支状态…`). What cannot be read counts as unmerged. A text round on an untouched branch passes (its snapshot is the base commit), so a deploy / code card that only reported is still accepted with `complete`.
    - Not checked: kinds `question` and `content` (their result is text), and cards in phase `todo` or `failed` (0.9.66: work settled outside the board can be marked done by the user). Both callers are checked alike: the user's button is refused too.
    - The tool `complete_todo` answers a refusal as a result, `{ ok: false, error: "COMPLETE_REFUSED", content: <the sentence above> }`, not as an exception. The RPC rejects with the same sentence.
    - Actor. The timeline entry is `标记完成` with actor `user` for the RPC, and `总管标记完成` with actor `chief` for the tool. Before #104 both were written as `user`. Entries written earlier are not rewritten.
    - Compatibility: a card marked done before #104 while its branch was unmerged stays `done`; nothing is reopened. Since the check awaits git, a card taken over by another write meanwhile is not completed (one `已丢弃` timeline line, as for the other write entries).
  - **Text deliverable** (`judgeTextDeliverable`, `src/server/text-deliverable.mjs`). A round that changed no file on a `question`, `content` or `deploy` card goes to the `deliverable` gate only when its last reply passes, in this order:
    1. `too_short`: at least 40 non-space characters (`MIN_DELIVERABLE_CHARS`, unchanged; no longer sufficient alone).
    2. `intent_tail`: the reply does not end by announcing the next step. Same test as `isSubstantiveReport` (`endsWithIntent`, last 120 characters; phrases 接下来 / 下一步 / 我会 / 我将 / 我先 / 让我 / 将去 / 然后 / 稍后 / 马上 / 即将 / 现在开始 / 准备 / 开始修改|动手|实现 / let me / I'll / I will / next, I; `让我` and `将去` are new). Exception, judged per small clause (the last sentence is cut at `，,；;` as well; a mark in an earlier clause never counts): the sentence holds no plan of the worker's own (我将|会|先|去|来|再|准备|打算 / 让我 / 将去 / I'll / I will / let me / going to), and its closing clause either opens with advice to the reader (建议 / 推荐 / 请你|用户|确认… / 由用户… / 待确认…, an optional connective such as 下一步 / 因此 first), or states a result (已完成|部署|上线|发布|合并|修复|验证|通过|生效 / an HTTP status / 返回 200 / an exit code) while the sentence has no future word (接下来 / 下一步 / 稍后 / 随后 / 马上 / 即将 / 将要 / 将会 / 准备 / 打算 / 再去 / 现在开始 / will). So `建议下一步由用户确认方案 A。` and `先构建然后重启，服务返回 HTTP 200。` pass; `初步分析已完成，接下来我将去读 X。` and `方案已整理，稍后我会执行。` are `intent_tail`.
    3. `no_evidence` (kinds `question` and `deploy`; not `content`, which is prose): the round made at least one tool call (host `tool_calls` after the last instruction), or the text has a concrete reference: a code span or block, a file path (two or more path segments, or a name with an extension, optional `:line`), a URL, a 7–40 hex commit id, or an exit code.
    4. `no_deploy_proof` (kind `deploy` only): the text shows a command output — a fenced block with content, or a line starting with `$ ` (a line starting with `#` or `>` is a Markdown heading or quote and is not one) — or has a small clause (cut at `。！？`, line breaks and `，,；;`) that reports as done an HTTP status (`HTTP 200`, `状态码 200`, `200 OK`, `返回 200`, `returned 200`), an exit code, or a named check result (健康检查 / 冒烟 / 回读 / 部署后校验 / 线上验证 / 校验 / 验证 … 通过 | 成功 | 正常 | 一致 | 失败 | 异常 …, both inside that one clause). A clause about what is still to come or conditional does not count: 等… (at the start of the clause, after 要/需/先/得/须, or followed by 再|才|后) / 等待 / 待确认|验证|部署… / 后再|后才|后即可 / 如果 / 假如 / 一旦 / 若 / 需要 / 应该 / 即将 / 将要|将会|将在|将于 / 我会 / 我将 / 稍后 / 随后 / 接下来 / 下一步 / 准备 / 打算 / 计划 / 即可 / 才能 / 方可 / 尚未 / 还没 / 暂未 / should / will / would / once / until / if / pending / need to / going to / to be; e.g. `等健康检查通过再切流量即可` is not a check result. Whatever else it contains, a report that says the deployment was not run (尚未|还没|暂未 + 执行|部署|上线|动手|发布|运行, `not (yet) deployed|executed|run`) has no deploy proof. Fail-closed on purpose: a real report that trips one of these words in the clause of its only evidence is asked once more for the output.
    - A reply that fails 2–4 is not delivered: nothing is written to `evidence.deliverable`, and the timeline gets `本轮回复（N 字，工具调用 K 次）不算交付：<原因>` (deploy cards add `；部署未记为已执行，请补充证据`). The line `部署已执行，未改仓库代码…` is written only for a reply that passed. The round then follows the idle path as before (up to 3 nudges in the same session, then the idle settlement); for `no_evidence` / `no_deploy_proof` the nudge names what is missing and asks for the commands, their output and the check result instead of `上一轮你只说明了打算`.
    - Compatibility: cards already at the `deliverable` gate are not re-judged. Code cards (`feature` / `bug`) keep `isSubstantiveReport`; the hand-back of a merged card's answer keeps the length test.
  - **Watches** (`todo_watches.active`). A card that ends keeps no active watch: `complete`, a proven merge (after the `merged` notice has been handed to the watching topics), `close`, and a stop by the user or Chief that puts the card back to `todo` (`cancel_build`; a stop with a platform reason, and a stopped review that leaves the card at its gate, keep theirs) set every watch of the card inactive, also those of topics that could not be notified (archived, missing, other project). Rows are kept with `active = 0`. A `done` / `closed` card that is dispatched again or reopened first ends whatever watches it still has (cards finished before #104 kept them) and writes `已清理 K 条旧订阅：…` on its timeline; the dispatch then watches it from its own topic only. No stored row is rewritten at startup.
  - **Digest clock** (`topics.lastDigestAt`, ms). It now means: the time up to which card updates were sent to this topic's Chief in a `Since your last turn:` block. It is set only by a launch that was accepted by the host, to the moment the digest of that launch was read (before: to the launch time, also for launches that carried no freshly read digest, so updates between the read and the launch were skipped). A wake that is queued (Chief busy, compression, deferred) or whose launch failed leaves it unchanged and is stored without a digest; the turn that delivers the queue reads the digest once and puts it in front of the merged wake text, so N queued wakes carry one batch instead of N copies. A launch without a digest (a failover relaunch) does not move the clock. Rows of other projects are filtered as before (#97).

No version is bumped. Before #109 the merge committed whatever the worktree held uncommitted (`git add -A` + commit) after the review binding (#103) had been checked; a file written in between was merged unreviewed, because HEAD then contained the snapshot (relation `ancestor`) and passed #102.

With a `snapshotSha` or an `expectedHeadSha`, `git status --porcelain --untracked-files=all` of the worktree must be empty (ignored files, such as the bootstrap dependency links, do not count). With an `expectedHeadSha`: it must name a commit (`期望合并的提交 <sha12> 在仓库中找不到`), and HEAD of the worktree, which the #102 check already requires to be the branch tip, must be exactly that commit, not a descendant: `工作树 HEAD=<sha12> 不是期望合并的提交 <sha12>（核对之后分支上又有了变化），请重新派发审查或重新确认后再合并`. This check and those of #102 are all applied; any one refuses.

In practice they are reached only when the worktree changed between the binding check and the merge; a change that is already there when the merge is requested is refused earlier, at the gate (#103 for a card with `reviewedSha`; the next item for a card without).
  - A card without `reviewedSha` that has a `snapshotSha` and uncommitted changes is refused by the review binding before any confirmation is asked, for the user and the Chief alike and whatever `confirmUnreviewedMerge` says: the card goes back to the merge gate (`gateOwner: human`), `lastError` = `拒绝合并 #<N>：工作树有 <n> 项未提交改动（<first 5 paths>[ 等]），合并不会自动提交它们。请先提交或清理再合并；也可以 run_review（派审查时会先提交这些改动并记录被审提交）。`, timeline `合并未执行：工作树有 <n> 项未提交改动（…），合并不会自动提交它们，请先提交或清理再合并；也可以派发独立审查（派审查时会先提交这些改动）`. The files may be the ones the snapshot was taken of (a build that ended without committing) or later ones; `git status` cannot tell them apart and the text does not claim either. Before #109 such a card was merged with those changes after the confirmation (`另有 <n> 项未提交改动会随合并一并提交`). This is the compatibility cost: a build that ended with uncommitted files (its snapshot is the synthetic commit) can no longer be merged without a review by confirming twice; dispatching the review commits the files (#103) and binds them, or they are committed by hand.
  - Automatic commit, narrowed. Only a card with neither `reviewedSha` nor `snapshotSha` (stored before snapshots existed, or whose snapshot could not be taken) still has its uncommitted files committed by the merge, after the confirmation of #103. The moment that commit is made the timeline gets (actor `system`) `为无审查快照的卡自动提交了 <n> 个文件（提交 <sha12>），这些改动没有经过审查，随本次合并进入 <base>`; the line is there also when the merge then fails. `<n>` counts files (untracked files one by one). The result of `mergeWorktreeBranch` gains `autoCommittedCount` (integer, 0 otherwise) and `expectedHeadSha` (full sha or `''`). There is no switch to bring the old behaviour back for cards that have a snapshot: such a card is unblocked by committing or by `run_review`, both of which leave a record.

- Merge proof (Todo #102, after 0.9.71). No column, no migration, no new RPC or tool, no change to any input or output model; five new `evidence` keys, new `lastError` / timeline texts, and a changed `merge_build` answer. A merge is written `done` only after it was proven, and the worktree and the task branch are deleted only after that proof.
  - Before the merge (`mergeWorktreeBranch`, each failure refuses the merge; nothing was merged, nothing is deleted):
    - the card has a branch, it is not the base branch, and it exists as a local branch: `卡片没有登记分支，没有可合并的内容` / `分支不存在：<branch>`;
    - the worktree path is a directory: `工作树不存在：<path>（分支 <branch> 仍在，未合并）`. A card with an empty `worktreePath` is refused the same way (before: it was written `done` without any merge);
    - HEAD of the worktree is on the card's branch: `工作树 HEAD 所在分支为「<actual branch | 游离 HEAD>」（HEAD=<sha12>），卡片登记的分支为「<branch>」，两者不一致`;
    - `snapshotSha`, when the card has one, names a commit of the repository (`卡片快照 <sha> 在仓库中找不到对应提交`) and HEAD of the worktree is that commit, contains it, or is a commit made from the uncommitted files the snapshot was taken of (same tree, and the snapshot's parent is in HEAD): otherwise `工作树 HEAD=<sha12> 与卡片快照 <sha12> 不一致`. A card without `snapshotSha` (`''`) skips this check only. Until #109 uncommitted files in the worktree were committed to the card's branch first (`git add -A` + commit); since #109 that happens only for a card that has neither a snapshot nor an expected HEAD (see Merge atomicity below).
  - A commit that is already an ancestor of the base branch is not merged again (no `git merge` is run, the main checkout is not switched).
  - After the merge: HEAD of the worktree (and the snapshot commit, unless it is the tree-only case above) must be an ancestor of the base branch (`git merge-base --is-ancestor`, exit 0). If not: `合并命令返回成功但快照提交未进入 <base>（<base>=<sha12>，应包含 <sha12>），已保留工作树与分支`.
  - Any of these failures: `phase: failed`, `gateOwner: human`, `gateKind: failed`, `evidence.mergeVerify: failed`, and `lastError` = the timeline line (actor `system`) = `合并失败（merge_verify_failed：合并校验未通过，未标记完成，工作树与分支已保留；核实后可调用 retry_merge 回到合并关口，审查结论保留）：<reason above>`. `branch`, `worktreePath`, `snapshotSha`, `diffs` and the rest of `evidence` are left as they were. The text starts with `合并失败`, so `retry_merge` accepts the card when its branch and worktree record are still there. `merge_verify_failed` is the marker to search for. The thrown error has `code: MERGE_VERIFY_FAILED` and `stage: pre | post`.
  - A proven merge writes `phase: done` as before, with `snapshotSha` = `evidence.commitSha` = `evidence.mergedSha`, and:
    - `evidence.mergedSha` (string, short sha; absent until a merge was proven): the base branch, read after the proof;
    - `evidence.mergeKind` (string): `merge_commit` (a new merge commit), `fast_forward` (the base branch now points at the card's commit; not produced by this plugin's own `--no-ff` merge, kept for honesty), `already_merged` (the base branch did not move);
    - `evidence.mergeVerifiedSha` (string, full sha): the commit proven to be an ancestor of the base branch;
    - `evidence.mergeSnapshotSha` (string, default `''`): the card's `snapshotSha` as it was before the merge replaced it;
    - `evidence.mergeVerify` (string): `passed` or `failed`; absent on cards merged before this change (their merge was never proven).
  - Timeline line of a proven merge, one per kind: `已合并至 <base>（<sha>，新合并提交；已验证 <sha12> 是 <base> 的祖先）`, `已合并至 <base>（<sha>，快进，未产生合并提交；已验证 <sha12> 是 <base> 的祖先）`, `分支提交 <sha12> 已在 <base> 中（<base>=<sha>），无需再次合并；已验证它是 <base> 的祖先` (before: always `已合并至 <base>（<sha>）`).
  - MCP tool `merge_build` answers by the card `mergeBuild` returned. `Merged #<n> (<sha>; <new merge commit | fast-forward | the branch was already contained in the base branch, nothing new was merged>; verified as an ancestor of the base branch) and marked done.` only for `phase: done` with `evidence.mergeVerify: passed`; `data`: `id`, `phase`, `commitSha` (`evidence.mergedSha`), `merged: true`, `mergeKind`. Otherwise `data.commitSha` is `''` and `data.merged` is `false`: a `done` card without that proof (`ok: true`, says this call merged nothing), a card in `merging` (`ok: true`, `... It is NOT marked done ...`), any other phase (`ok: false`, `error: MERGE_NOT_COMPLETED`, names the phase). Before: every returned card was answered `Merged #<n> (<snapshotSha>) and marked done.`
  - Compatibility: cards stored before this change are not rewritten. Their `done` state carries no `mergeVerify`; whether their commit is in the base branch can only be read from git.
- Merge retry and per-card write lock (since 0.9.48). No column, no migration, no new `evidence` key.
  - State machine: `failed` gains the event `RETRY_MERGE` → `review`. It is the only way from `failed` back to the merge gate; every other exit of `failed` is unchanged.
  - A failed merge (`MERGE_FAILED`) writes `phase: failed`, `gateOwner: human`, `gateKind: failed` and `lastError` only. `branch`, `worktreePath`, `snapshotSha`, `diffs` and `evidence` (`reviewVerdict`, `reviewSummary`, `testRc`, `gateSkipped`, …) are left as they were; the main checkout is restored by `git merge --abort` and the worktree and task branch are not removed. `lastError` (string, always starts with `合并失败`) is now `合并失败（[冲突文件：<a>、<b>；]处理后可调用 retry_merge 回到合并关口，审查结论保留）：<git error>`: the conflicting files (at most 20, taken from `CONFLICTS: <file>:<kind>, …` in the git error; the part is omitted when the error names none, e.g. a dirty main checkout) and the hint come before the raw error so the 0.9.x `lastError` length cap cannot cut them off. A refusal throws a Chinese error, writes `重试合并没有执行：<原因>` on the timeline and changes nothing else. A missing worktree is never recreated (that would drop the unmerged changes): the card has to be rebuilt.

A lock older than the TTL is taken over by the next write, and its former holder does not release the new holder's lock. (The three new `evidence` keys of 0.9.49 belong to other items: `reviewInconclusiveRetries` to the review verdict item below, `testFailures` and `testFailureCount` to the test gate runtime item further down.)

Rule (`parseReviewVerdict`, applied to the last assistant message with text of the review session, upper-cased): (1) every `VERDICT: APPROVED` / `VERDICT: CHANGES_REQUESTED` in the text is found (the colon may be ASCII `:` or full-width `：`, with any spaces around it; any markup around the line: code block, quote, bold) and the last one is the candidate, as the review prompt and the request for a verdict ask for the verdict on a line of its own as the last line; (2a) when the line of that last occurrence names both verdicts (it contains the token `CHANGES_REQUESTED` and the word `APPROVED`, e.g. `VERDICT: APPROVED or CHANGES_REQUESTED`) → `inconclusive`: a template or a question, not a verdict; (2b) when the last occurrence is `APPROVED` and a `VERDICT: CHANGES_REQUESTED` line (either colon) is anywhere in the text → `inconclusive`, and the reviewer is asked once for one verdict. Both verdict lines in one text is either an approval that quotes the rejection line (a review describing this rule) or a rejection followed by a conditional approval (`VERDICT: CHANGES_REQUESTED` … `修好后可以改成 VERDICT: APPROVED`); no attempt is made to tell the two apart. The check is one-sided on purpose: a rejection read as approved can be merged by the Chief, an approval read as rejected only stops the card. A bare `CHANGES_REQUESTED` without `VERDICT:` in front does not trigger it; (2c) otherwise the last occurrence decides: `approved` or `changes_requested` (so `VERDICT: APPROVED` earlier and `VERDICT: CHANGES_REQUESTED` last is `changes_requested`). History: up to 0.9.48 `VERDICT: CHANGES_REQUESTED` anywhere beat `VERDICT: APPROVED`; a text with exactly one verdict line is judged as it was then, and a text with both lines that ends with `APPROVED` changed from `changes_requested` to `inconclusive`. Steps 3–6 apply only when the text has no verdict line at all; (3) when the text waits for a later turn (`稍后`, `稍候`, `待会`, `等会`, `回头再`, `随后再/继续/给/补`, `下一轮`, `下一回合`, `等…再`, `待…后/完…再`, `还在/仍在/正在` + `跑/运行/执行/进行/等`, `尚未/还没` + `跑完/完成/结束`, `然后/之后/再/才` + `给(出)结论`, `will continue`, `I'll continue`, `to be continued`, `continue once/after/when`, `still running / in progress / waiting / pending`, `in progress`, `next turn`, `not yet`, a negation (`not`, `n't`, `no`, `cannot`) and `yet` in one sentence, `will` / `I'll` and `later` in one sentence in either order (up to 0.9.49 the bare words `yet` and `later` anywhere; narrowed in 0.9.52, see below), `once/after/when/until it/they/the/that/this … finish/complete/done/end`, `verdict will/to follow`) → `inconclusive`; (4) else contains the token `CHANGES_REQUESTED` → `changes_requested`; (5) else contains the word `APPROVED` → `approved`; (6) anything else, empty or missing text included → `inconclusive`.   - Declaration: the file `.node-version` in the root of the task worktree is the only source for the node the test gate runs on. First line that is not empty and does not start with `#`; accepted forms `22`, `22.13`, `22.13.0`, with an optional leading `v` and trailing `.x`. `22` matches any `v22.*.*`, `22.13` any `v22.13.*`, `22.13.0` that version only. Anything else (empty file, `lts/*`, a range such as `>=22`) is an unusable declaration. "No declaration" means only that the worktree has no directory entry of that name (`lstat` reports `ENOENT`). An entry that exists but cannot be read is an unusable declaration too, and the command is not run: a directory (`EISDIR`), a file without read permission (`EACCES`), a dangling link (`lstat` succeeds, reading reports `ENOENT`; shown as `链接指向的文件不存在，ENOENT`), or any other read error. `engines.node` in `package.json` is not read by the gate, and the gate does not combine the two: the declaration alone decides. A project that states a floor in `engines.node` must therefore write a declaration that is not below the floor, i.e. one that matches no version under it: with `engines.node` `>=22.13.0`, `22` would also match `v22.5.0`, so the minor has to be written. In this repository `engines.node` (`>=22.13.0`) is the floor for the Studio host process and `.node-version` is `22.23`: the `v22.23.*` line the tests are developed, gated and run in CI on (`.github/workflows/check.yml` reads the same file through `node-version-file`). A test compares the two (major, minor, and the patch when the declared minor is the floor's). Moving to a newer line is an edit of that one file.
  - Selection (`resolveGateNode` in `src/server/gate-runner.mjs`): every `node` on the `PATH` of the plugin host is asked for `--version` (at most 5 s each, in `PATH` order, the same binary once, compared by its real path); the first one that matches the declaration is used. The selected path is always absolute and is the `PATH` entry itself, not its real path (a version manager's `node` can be a link to a launcher that decides by the name it is called with); a relative `PATH` entry is resolved against the worktree first, then against the directory of the plugin host. The whole search, the install directories below included, has a total budget of 15 s: when it is used up no further node is asked and the gate fails as described under "Declared but not available", with `解析超时` in the summary. Without a declaration the same budget only limits the lookup of the version shown in the verdict. When none matches, the same is done for the usual install directories of the declared major: `/opt/homebrew/opt/node@<major>/bin`, `/usr/local/opt/node@<major>/bin`, the `v<major>.*` directories of nvm (`$NVM_DIR` or `~/.nvm`), Volta, fnm, asdf and mise (newest first), `~/.local/bin`, `/opt/homebrew/bin`, `/usr/local/bin`. A node that does not start (non-zero exit, no version line) is never selected. The command then runs through the shell as before, with a temporary directory that holds only a `node` link to the selected binary put first on its `PATH` (the directory is removed when the gate ends); the rest of the host environment and `CI=1` are unchanged, so `npm`, `npx` and `#!/usr/bin/env node` scripts resolve to the selected node while every other tool keeps its place on `PATH`.
  - No declaration file: nothing is selected and nothing is put on `PATH`; the command runs on the host `PATH` as it did before 0.9.49 (projects that are not node projects need no file). The verdict then says `node <version> 未声明` (`node 未声明` when the host `PATH` has no working node).
  - Declared but not available: the command is not run. The result is `testRc: 127`, `testSummary: Failed (rc=127, 0.0s, node 未找到) | 期望 node v22.x（.node-version），当前 PATH 里找到的是 v26.12.1（/path/to/node）[、…]；常见安装目录里也没有 v22.x，未执行验收命令` (up to 3 nodes found on `PATH` are listed, a node that does not start as `无法启动（<path>）`; `PATH 里没有 node` when there is none). A node that did not answer within its 5 s is listed as `未响应（<path>）`. When the 15 s budget runs out: `Failed (rc=127, 15.0s, node 未找到) | 期望 node v22.23.x（.node-version），解析超时：15s 内检查了 3 个 node 都不符合，其余未检查；当前 PATH 里找到的是 未响应（/a/node）、未响应（/b/node）、未响应（/c/node），未执行验收命令`. A command that cannot be started at all (for example the worktree directory is gone) gives `testRc: 127` and `Test command failed to spawn (node v22.23.2): <error>`, cut to 600 characters like every other summary. - Reply identity and attempt boundaries in the live stream (since 0.9.53). Client only: no model, RPC, tool, column or stored value changes, and nothing is migrated; the host is unchanged. `applyStreamEvent` keeps an in-memory `reply` record in the stream buffer (`{ turnId, base, segs, ends, sealed }`, never sent or stored; `null` / absent by default and reset to `null` wherever `text` is reset in `App.jsx`: `run.started`, `run.queued`, a replay on `resumed`; the end of the turn replaces the whole buffer). A `message.delta` with a valid identity (`turn_id` / `turnId` a non-empty string, `segment` and `offset` non-negative integers; `offset` counts UTF-16 code units of the segment already sent) is upserted: a chunk ending at or before what the segment already holds is dropped and asks for no flush, a chunk that overlaps it adds only its new tail, a chunk past it (a missed frame) is added and the segment end moves to `offset + length`. Each segment only records the furthest position reached, so a missed frame is not filled in by a later replay: the replayed frames lie before that position and are dropped.（即：漏帧不会被重放补回。） A `message.interim` with `turn_id` and `segment` seals that segment once: with `already_streamed: true` its text is compared with the streamed text after collapsing whitespace the way the host does (`\s+` to one space, trimmed): when the segment collapses to the same text or a longer one, the streamed text is kept as it arrived (its blank lines included); when the sealed text collapses to the streamed text plus more, only that unstreamed tail is added after it; when they are unrelated the sealed text is appended; on an empty segment it is added unless the text on screen already ends with it after collapsing. Without `already_streamed: true` the seal behaves as in the first 0.9.53 build: an empty segment takes the text, a raw-prefix match replaces or keeps it, anything else is appended; a re-sent seal and later deltas of a sealed segment are dropped. A `message.start` or reply frame with a different `turn_id` empties `text` and `reasoning` and starts a new record; the first identified frame of a buffer keeps the text already on screen. Frames with missing or malformed identity are appended as before 0.9.53 and never throw. `reasoning.delta` carries no identity: `reasoning` is emptied by a `thinking.delta` line that announces a new attempt (`retrying`, `trying fallback`, `next pool credential`; not `retrying won't help`), by a new seal and by a new `turn_id`; the line itself is kept in `status` only. Not covered: after a `resumed` without replayed events the page shows the host's `output` text, and if the host then re-sends that turn's frames from offset 0 they are added after it.
- Reasoning replay and `status.update` in the live stream (#81, 0.9.69). Client only: no model, RPC, tool, column or stored value changes, and nothing is migrated; the host is unchanged. Why: the host sends its retry/fallback lines as `status.update` (`{kind, text}`), not `thinking.delta`, buffers them and drops them when the retry succeeds, so after a successful empty-response retry the client gets no line and the second attempt's reasoning was appended to the first. (1) `status.update` is applied only while the buffer is already working (`isWorking` true): the host also sends it between turns (`ready` after a manual compaction or when the session lock is busy, `compacted`), so it never sets `isWorking`, `startedAt` or the turn boundary, and on an idle buffer it changes nothing and reports no change. While working, the trimmed `text` (the `kind` when there is no `text`, read as kind `status`) goes to `status`, latest wins, like `thinking.delta`; an empty one changes nothing; `ready` with kind `status` only empties `status` and is never shown. It empties `reasoning` only when `kind` is `fallback`, or `kind` is `status`, `lifecycle` or `warn` and the text announces a new attempt; any other kind (`compacting`, `compacted`, …) never touches `reasoning`. (2) The attempt wording, for both `thinking.delta` and `status.update`, is now `retrying`, `trying fallback`, `next pool credential`, `reconnecting`, `switching to fallback` / `switched to fallback` (not `retrying won't help`, `stop retrying`, `keep retrying`). (3) Replay check on `reasoning.delta`, with or without any line: when chunks arrive that equal the start of the reasoning already held, the earlier copy is dropped and the new attempt kept, once the replayed part covers the whole earlier reasoning (at least 8 UTF-16 code units, `REPLAY_MIN_WHOLE`) or at least `max(32, ceil(earlier length × 0.5))` units of it (`REPLAY_MIN_CHARS`, `REPLAY_MIN_RATIO`); text that starts with the whole earlier reasoning replaces it only when that earlier reasoning is at least 8 units and at least half the length of the new text. A long reasoning that quotes its own opening mid-way therefore stays whole; the cost is that on a long reasoning the duplicate stays on screen until the replay has covered half of it. Until then the chunks are shown as normal text; a chunk that stops matching ends the check and nothing is removed. The pending check is kept in the buffer as `replayTail` (string, default `''`, in memory only; ignored when `reasoning` no longer ends with it, so outside resets need no change). Not covered: a retry whose reasoning differs from the first attempt is only separated when a boundary line arrives; a host-side identity on `reasoning.delta` (`turn_id` / attempt / offset) would be needed for that.

An ambiguous call is let through only when every candidate topic owns the card's project (for `list_todos`: when all candidates have the same project); otherwise it is refused with `error: CALLER_AMBIGUOUS` and `无法确定调用方话题，请显式传 topic_id（参数 caller_topic_id，填你所在话题的 id，即指令里 Current Topic 的 topic_id）。当前有 N 个总管会话可能是调用方：「<title>」（<id>）、…；调用未带会话身份，为避免跨项目误操作已拒绝，未做任何改动。`. `caller_topic_id` (optional string, at most 120 chars, on `list_todos` and on every tool with `todo_id`; never passed on to the tool's own handler) settles it, under two conditions that both rest on host events and not on the caller's word (since #108): the named topic (a) is one of the candidates of this call and (b) its `chiefSessionId` has this very tool open in `openToolCalls` (under its own tool name only, started at most 120 seconds ago; a `tool_call` wrapper is no evidence, because it shows that the session is calling some tool, not which one). Then that topic is the caller (`declared`) and the usual rule applies to it. Every other value is refused, and the call with it, whatever the candidates own: `ok: false`, `error: CALLER_AMBIGUOUS`, nothing done. `resolveChiefCaller` then answers `declaredUnknown` (the value) and `declaredRefusal`: `not-candidate` — the value names no candidate, e.g. the topic of another project's Chief that runs but does not have this tool open in the tier that was read, an unknown id, or any value when there is no candidate at all (text `caller_topic_id <id> 不是当前可能在调用的总管话题`; `当前没有可核实的总管调用方` when there is no candidate) — or `no-open-tool` — the value names a candidate that does not have this tool open under its own name: the candidates are known from `tool_call` wrappers (text `caller_topic_id <id> 无法核实：该话题的总管会话是经 tool_call 包装调用的，包装看不出里面是哪个工具，不能当作开着本工具的证据`) or from running Chiefs only (`active-run`, text `caller_topic_id <id> 无法核实：没有看到该话题的总管会话正开着本工具，仅凭「总管正在运行」不接受自报`); in both a declaration is never accepted, a true one included. A declaration is so accepted in the by-name tier only. The refusal text of a declaration that was not believed starts with `无法确定调用方话题：` and ends with `caller_topic_id 只能填你自己所在话题的 id（指令里 Current Topic 的 topic_id），且只在看到你的会话按工具名直接开着本工具时才被采信（经 tool_call 包装调用不算）；请改为直呼工具名后重试，仍被拒绝请让用户在页面上操作。`; the text of a refusal without a declaration ends with `caller_topic_id 只在你的会话按工具名直接开着本工具时才被采信，经 tool_call 包装调用时请改为直呼工具名。`. Changed with #108: before it, a value naming any running Chief's topic was accepted on `active-run`, with no candidate a value naming any non-archived Chief topic was accepted, and a value naming no candidate was refused only when not every candidate owned the card's project; a Chief could so act for another project by naming its topic. Nothing stored changes; a call without `caller_topic_id` behaves as before. `caller_topic_id` is ignored when the call carries a session id. The Chief instructions give the topic id and say when to send it. One running Chief, or one Chief with the tool open, is never ambiguous. Known cost of fail-closed (by design, not a defect; since #97, recorded with #108): when a Chief session and a session that is no Chief (a plain chat, a build or review worker) have the same tool open at the same time in the same tier, and the card is not of that Chief's project, the call is refused with `CALLER_AMBIGUOUS` whoever makes it — the non-Chief session is refused together with the Chief, although on its own it is not restricted. Nothing in a call without a session id tells the two apart, and letting it through would let the Chief act on a card of another project. The non-Chief session cannot lift the refusal with `caller_topic_id` (it is no Chief topic's session); it repeats the call once the Chief's tool call has ended (its entry leaves `openToolCalls` with `chat.tool.completed` / `chat.tool.failed`, the end of the run, or after 120 seconds), or the user acts on the page (RPC is not guarded). A card of the Chief's own project is not affected: the call is let through. Remaining limits: a call made through a `tool_call` wrapper cannot be tied to a tool (the host event names the wrapper, not the tool inside), so in the wrapper tier `caller_topic_id` is always refused, a true one included — a Chief that calls through a wrapper and is answered `CALLER_AMBIGUOUS` cannot settle it by declaration and has to call the tool directly by its own name (or the user acts on the page); two Chiefs that both have this very tool open under its own name at the same time are both verified candidates, so one that names the other's topic in `caller_topic_id` is still taken for it (host events carry no call id that would tell the two calls apart; the window is the overlap of two direct calls of the same tool, not of any two tool calls); a Chief whose tool event the host has not delivered yet cannot settle an ambiguous call by declaration and has to repeat it; a call from a Chief whose run and tool events the host did not deliver is taken for a non-Chief call; a plain session whose tool events the host does not deliver is taken for the running Chief of another project and refused, with `（调用未带会话身份，按正在运行的总管会话判定）` at the end of the text.

  - `settings.confirmUnreviewedMerge` (boolean, default `true`; `save-settings` input `confirmUnreviewedMerge`, kept when another field is saved; not in the plugin `configSchema` and not on the settings page yet).
  - Verdict rule (`parseReviewVerdict`, last assistant message with text of the review session; four outcomes as before, `review_failed` being the failed run). What changed: approval needs the sole last line; no verdict line no longer falls back to the bare word `APPROVED`.
    - (0) Code is not read: fenced blocks (a line starting with three or more backticks or tildes; an unclosed fence runs to the end) and inline code spans are removed first.
    - (1) The last line (trailing blank lines and lines without a letter or digit are skipped) is a sole verdict line when the whole line, without leading/trailing spaces, a heading mark, attached emphasis marks (`**…**`, `__…__`) and trailing `.`/`。`/`!`/`！`, is `VERDICT`, a colon (`:` or `：`), and exactly one verdict word; case does not matter. Approving word: `APPROVED`. Rejecting words: `CHANGES_REQUESTED` (also with a space or a hyphen), `NOT APPROVED` (also `NOT_APPROVED`, `NOT-APPROVED`, and `NEVER` / `CANNOT` / `CAN'T` / `DON'T` / `WON'T` / `ISN'T` / `不予` / `不能` / `无法` / `暂不` / `拒绝` / `未` / `不` in front of `APPROVED`), `不通过`, `驳回`, `需修改`, `需要修改`, `不可合并`. Anything else on the line makes it no sole verdict line: a label in front (`结论：VERDICT: APPROVED`), a condition or note behind (`VERDICT: APPROVED，前提是…`, `VERDICT: APPROVED（必改：…）`, `VERDICT: APPROVED but must fix …`, `VERDICT: APPROVED 需修改`), quote marks, a list or block-quote prefix, both verdicts.
    - (1a) Sole last line approves → `approved`, unless a rejecting verdict stands anywhere else in the text → `inconclusive`. This one check reads the whole text, code included (a `VERDICT:` followed by a rejecting token anywhere, or an earlier rejecting line of its own): `VERDICT: CHANGES_REQUESTED` … `修好后可改成` + last line `VERDICT: APPROVED` is not an approval, also when the rejection was written in backticks. So with several verdict lines the last sole line decides, except that an approval never overrides a rejection.
    - (1b) Sole last line rejects → `changes_requested`, whatever the text above says (waiting words included).
    - (2) No sole verdict line as the last line → never `approved`: (2a) waiting words (the list of 0.9.49 / 0.9.52 above) → `inconclusive`; (2b) the line of the last `VERDICT: <APPROVED | CHANGES_REQUESTED>` outside code names both verdicts → `inconclusive`; (2c) that last one rejects → `changes_requested` (`VERDICT: NOT APPROVED，三处必改见上`, a rejection line followed by its findings), it approves or is negated into nothing → `inconclusive` (`VERDICT: APPROVED` followed by `必改：…` on the next line; `VERDICT: APPROVED` in a sentence); (2d) no such `VERDICT:`: a rejecting line of its own that is not last (`VERDICT: 驳回` + findings) or the bare token `CHANGES_REQUESTED` → `changes_requested`; everything else → `inconclusive`, including the bare word `APPROVED` (`Looks correct. APPROVED.` was `approved`), prose such as `驳回，见上面三条。`, and empty text.
    - Changed outcomes against 0.9.71, all from `approved` to `inconclusive`: a verdict line that is not the last line (`VERDICT: APPROVED` + a summary below it), a verdict sharing its line with other text, a verdict in a code block or inline code, the bare word `APPROVED`. The reviewer is asked once in the same session as for any `inconclusive`; the request text now says the line must be the sole last line, without backticks, quotes or a condition. Rejections are read as before, plus the Chinese words above on a line of their own. Known cost, in the safe direction: an approval that quotes a rejection line, or adds an emoji or a note to the verdict line, is asked once more instead of being approved.

## Search (`search-workspace`, Todo #98)

One read-only RPC serves the command palette (⌘K all / ⌘P tasks / ⌘J topics), the board search box, the project workspace task search and the memory search. Implementation: `src/server/search.mjs`; matching helpers shared with the client: `src/shared/search-text.mjs`.

- Input `searchWorkspaceInput`: `query` (string, may be empty), `scope` (`all` default | `todos` | `topics` | `projects` | `memories`), optional `projectId` (todos of that project; topics of that project or without one; that project), `topicId` (todos of that topic), `memoryScope` (`all` | `chief` | `project` | `agent`), `limit` (per group, default 20, 1–100; contract rejects > 100, the server also clamps).
- Output `searchWorkspaceOutput`: `{ query, scope, recent, truncated, groups: [{ type, items, total, hasMore }], total, hasMore, tookMs }`. Each item: `type` (`todo` | `topic` | `project` | `memory`), `id`, `number` (todo), `title`, `snippet`, `matchedField`, `score`, `projectId`, `topicId`, plus display fields (`projectName`, `phase`, `kind`, `branch`, `archived`, `memoryScope`, `category`, `updatedAt`). With `scope: all` the groups (order todos, topics, projects, memories) together return at most `max(limit, 50)` items; a group with no room left still reports its `total`.
- Query: NFKC-normalised (full-width `＃１２` → `#12`), whitespace collapsed and trimmed, cut to 200 characters (`truncated: true`). `query: ''` returns recent items (`recent: true`: todos by `updated_at` desc, unarchived topics pinned first, projects by creation, memories pinned first). A whitespace-only query returns empty groups. Special characters never throw.
- Matching: `instr(lower(field), lower(query)) > 0` — a literal substring test; `%`, `_` and `\` are ordinary characters (no LIKE). `lower()` only folds ASCII; the query is folded the same way (`foldCase`). Chinese is never split into words. A query with spaces also matches when every term (at most 5) hits somewhere in the row (`matchedField: terms`, lowest rank). `#N` or bare digits also equal the card number.
- Fields and rank (`SEARCH_FIELD_SCORES`; first matching field wins; ties → `updated_at` desc, then number desc):

  | type | field (`matchedField`) | score |
  |---|---|---|
  | todo | `#N` = number (`number_hash`) | 1100 |
  | all | title exact (`title_exact`) / prefix (`title_prefix`) / substring (`title`) | 1000 / 900 / 800 |
  | todo | bare digits = number (`number`) | 700 |
  | todo | branch 600 · tags 560 · builder/reviewer Agent name (`agent`) 540 · project name/alias (`project`) 520 · topic title (`topic`) 500 | |
  | topic | brief goal 460 · progress 450 · next 440 · waitingOnYou / waitingTitle / blocked (`brief_waiting`) 430 | |
  | project | GitHub repo / repo path / remote (`repo`) 460 · description 420 (title = name or alias) | |
  | todo / memory | spec (`spec`) / memory content (`content`) | 400 |
  | todo | last error (`last_error`) | 350 |
  | todo | timeline event text (`timeline`) | 300 |
  | todo / topic | worker chat text (`chat`) / topic message text (`messages`) | 200 |
  | all | every term somewhere (`terms`) | 100 |

- Snippets are cut in SQL with `substr()` (240 characters around the hit; timeline / chat / messages: the newest matching entry) and then to about 100 characters with ellipses; the full spec, timeline or conversation never enters the response or the board snapshot. Stubbed cards (snapshot stage 7) are found by their stored spec / timeline because the search reads storage, not the snapshot.
- Cost: one SQL statement per group under `(user_id, profile)` (`idx_todos_scope` etc.), `COUNT(*) OVER ()` for `total`, `LIMIT` in SQL, no per-row queries; the CASE stops at the first hit so JSON scans of timeline / chat / messages run only for rows nothing cheaper matched. Measured (tests/t98-search-workspace.test.mjs): 1,000 cards + 10,000 timeline rows + 4,000 chat entries, p95 ≈ 30 ms on the maintainer machine.
- Client: the palette renders server groups (no slicing before filtering; cmdk `shouldFilter={false}`) with `#number`, project, phase, the matched field label and `<mark class="ot-mark">` highlights; action rows are filtered locally with the same `matchesQuery`. Requests are debounced 300 ms; an answer older than the newest request is dropped (host RPCs cannot be aborted); nothing is sent while an IME composition is open, and the Enter that closes a composition does not select a row. Empty result: explains which fields were searched, with a clear button; first load: skeleton rows; error: message + retry. On phones (≤ 780 px) the palette is full screen. The board search box filters loaded cards at once with `todoSearchFields` + `matchesQuery` (title, `#number`, branch, tags, Agent, project, topic, spec, last error, timeline) and adds the server hits (stub cards, chat hits); hits that are not loaded on the board (`todosOmitted`) are counted in the filter popover and the 「还有 N 张卡未加载」 note. The project workspace task search uses `scope: todos, projectId`; branch search stays local and also matches `#number`, author (`project-branches` now returns `author`), last commit subject and date (YYYY-MM-DD). `project-branches` annotates branches with this project's cards only (it used to pass a bare id as the filter and read every project's cards). Settings memory search and `db.listMemories({ query })` use the same `matchesQuery`.

## Host Integration Boundaries

- Multi-engine sessions run through `ctx.host.sessions.*` (`create`, `setWorkspace`, `setModel`, `run`, `stop`, `messages`, `connect`) bound to the caller's authenticated Studio profile.
- Live engine model catalogs and supported `reasoningEfforts` are queried dynamically via `ctx.host.agents.models(id)` and `ctx.host.models.list()`.
- Background reconciliation runs inside `apply(ctx)` via `ctx.scheduler.every('reconcile-loop', intervalMs, 'reconcile')` and `ctx.events.on('chat.*', ...)`, never inside 120-second RPC handlers.
- Follow-up syncs after a Chief turn ends run in the `settle` action via `ctx.scheduler.every('settle-loop', 2000, 'settle')`. Event and RPC callbacks only record which topic needs it (in memory, at most 200 topics); they start no timer, because a callback's `run.host` is cancelled once the callback returns. Output `settleResult`: `ok` (always true), `pending` (topics still waiting, 0 when none), `settled` (topics changed by this pass). Schedule per topic: first pass about 1s after the turn was seen finished, then up to 3 retries about 2s apart; it stops early when a pass adds nothing and the host tail is unchanged, or when a new turn has started. No stored data changes shape; pending entries are lost on reload and the reconcile loop then covers the 8 most recent topics.
- Chief transcript sync reads the newest 80 host rows and pages back with `offset` (80 rows per page, at most 12 pages) until a page contains a host message the topic already holds. `topic_messages.host_message_id` is the only idempotency key: two host messages with the same text are two rows. Matching by text and time (within 120s) is used only against a stored Chief message whose `host_message_id` is empty.
- `topic_messages` has a unique index `idx_topic_msgs_host` on `(topic_id, host_message_id)` for rows where `host_message_id` is not empty; inserting a second row for the same pair is skipped and reported as not added. Migration (runs once, when the index is missing): rows that repeat a `(topic_id, host_message_id)` pair are deleted, keeping the row stored first; rows with an empty `host_message_id` are not touched. If the index cannot be created the plugin still loads and the insert checks for an existing row instead. An older plugin version can open the migrated file; the index only makes its duplicate insert fail for that one message.
- Sending a message (since 0.9.42). `send-topic-message` takes an optional `clientNonce`: 1-64 characters from `A-Z a-z 0-9 _ . : -`, made by the page for one press of send. Omitted, empty or with other characters: the message is stored without a nonce and nothing below about nonces applies (behaviour before 0.9.42). Order of work on the server: (1) validate the input and the topic; (2) if this topic already holds the nonce, as a message or as a queued follow-up, store nothing, start nothing and return the current state; (3) if the topic is not known to this process as running, or `interrupt` is true, store the `kind: "human"` message and emit `board.updated` with `reason` `topic.message.accepted:<topicId>`; (4) only then probe the session and the engines and start the Chief. If the topic is known as running the message is not stored as a bubble first: the probe decides, and a busy topic gets a queued follow-up (`topic_queue`, reason `topic.message.queued:<topicId>`). If step (3) stored the bubble and the probe then finds a run started outside the plugin, that bubble row is deleted and the message becomes a queued follow-up with the same nonce. `drainTopicQueue` and `promote-topic-queue-item` also store the bubble and emit `topic.message.accepted:<topicId>` before probing engines.
- Stored fields (since 0.9.42). `topic_messages.client_nonce` and `topic_messages.send_error`, `topic_queue.client_nonce`: `TEXT NOT NULL DEFAULT ''`, added with `ALTER TABLE` on first start; rows stored before keep `''`. Unique index `idx_topic_msgs_nonce` on `(topic_id, client_nonce)` for rows where `client_nonce` is not empty: a second insert for the same pair stores nothing. In `stateSnapshot`, `topics[].messages[].clientNonce`, `topics[].messages[].sendError` and `topics[].queuedItems[].clientNonce` are strings and are present only when not empty, so a snapshot of older data is unchanged. `sendError` is the text of the error the call failed with (the same readable text as `topics[].lastError`), cut to 500 characters. It is written when the Chief could not be started for that message and is never cleared; the message row is kept. `send-topic-message` fails with that error when the launch failed before the call answered; see the time limit below. Unique index `idx_topic_queue_nonce` on `topic_queue(topic_id, client_nonce)` for rows where `client_nonce` is not empty: before it is created, rows sharing a topic and a non-empty nonce are reduced to the earliest (`created_at`, then `rowid`); inserting a second row for the same pair stores nothing.
- Order (since 0.9.42). Topic messages and queued follow-ups are read `ORDER BY created_at ASC, rowid ASC`: two rows with the same millisecond keep the order they were stored in.
- `board.updated` reasons `topic.message.accepted:`, `topic.message.queued:` and `topic.message.failed:` are read by the page at once. Every other reason stays in the page's refresh window (one `get-state` in flight, the next not earlier than 800 ms after the previous one started). The event name, payload shape (`at`, `reason`) and audience are unchanged; `topic.message.accepted` and `topic.message.failed` are new values of `reason`.
- The page (since 0.9.42) draws the user's bubble when send is pressed (`data-send-state="sending"`), keyed by the nonce, and replaces it with the stored message carrying the same `clientNonce` (`stored`, or `failed` when `sendError` is set). A stored message is drawn once per id and once per nonce. A send whose nonce is on a queued follow-up is shown in the queue tray only. Unconfirmed bubbles live in page memory only: after a reload, a reconnect or a topic switch the list is what the server stored. A send that failed before the server stored it keeps its bubble with `未发送：<reason>` until the next send in that topic or a reload; the composer gets the text and files back by the 0.9.27 draft rules. When no topic is selected the bubble appears after `create-topic` answered.
- Time limit of a send (since 0.9.42, replaced in 0.9.65). `send-topic-message`, `promote-topic-queue-item`, `message-todo` and the `message_todo` tool wait for the whole launch (busy probe, engine probe, session, host run) and return its result or error. They never return early: the host handle of a call is valid only until the call returns, and a launch left running after the answer was cancelled by the host (`sessions.run rejected`). Nothing calls the host after the call has returned; background work runs in the scheduler actions (`reconcile`, `settle`), which get their own handle each tick. The page sends without taking its busy lock, so it does not wait on this call. A refused host run is logged as `warn` with the reason in the message text.

- Chief context and slash commands (since 0.9.43). The plugin does not compress or run any command itself; the page sends the host's own command text over its live Chief session handle (`ctx.host.sessions.connect(chiefSessionId, …).run('/compress')`) and reads the host's answer from that subscription: `session.command` (`ok`, `action`, `message`; for compress also `beforeTokens`/`afterTokens`; for context `totalTokens`/`contextWindow`/`contextPercent`) and `compression.started` / `compression.completed`. Read-only. - Manual compression (since 0.9.43), in this order: (1) before every compression the page sends `/context` and waits up to 8 s for `session.command` `action: context` (this also gives the token baseline for step 4, in the host's `/context` unit) — a `run.started`/`run.queued` instead means the host passed the text to the model: the page stops that run (`stop-topic-run`), records `outcome: unsupported` and disables the button; no answer within 8 s is one failed attempt, recorded `outcome: timeout` (`宿主 8 秒内没有回应 /context，本次未压缩，可重试`): the button stays usable and a later `get-topic-context` answer applies again (only a passthrough makes `unsupported` stick until the topic changes); (2) `begin-topic-compress` takes the lock and answers its `lockId`, refused with a Chinese reason when the topic has no Chief session, a compression is already locked, a Chief turn is being started or drained, or the session is busy (busy probe, at most 1.5 s, fail closed); (3) `/compress` is sent and the page waits up to 120 s for `session.command` `action: compress`; (4) with no answer by then it sends `/context` again and counts a drop below 80 % of the step-1 total as success; (5) `record-topic-command` is called with the `lockId`: it releases the lock and writes a `kind: system` message: `上下文已压缩：<before> → <after> tokens`, `上下文没有可压缩的内容，宿主未改动` (host `compressed: false`, passed as the optional `compressed` input), `压缩失败，上下文未变，可重试：<host message>`, `压缩超时，上下文未变，可重试` or `当前大总管会话不支持手动压缩：…`. A `/compress` the host hands to the model is stopped like the probe and recorded `unsupported`. Detach: when the page leaves the session before the answer (topic switch: another session attaches), the command settles as `detached`; nothing is recorded, no system message is written and the lock stays until it expires (the host keeps compressing without the socket). A detach followed by the same session attaching again keeps waiting; the timer firing while detached also settles as `detached`, never `timeout`. Only the topic's `chiefSessionId` is compressed; build and review sessions are never addressed.

- Snapshot trimming never deletes stored data; it only shortens the `stateSnapshot` value, and each stage stops as soon as the value fits 1,500,000 bytes. Order: (1) diff bodies, finished todos first (`diffs[].hunkOmitted`); (2) worker chat of finished todos down to the newest 12 entries (`todos[].buildChatTrimmed`); (3) older topic messages, archived topics first and then the least recently active, keeping the newest 60 and then 20 per topic (`topics[].messagesOmitted` = number of older messages left out; absent when none); (4) worker chat of finished todos down to the newest 2 entries, oldest todos first; (5) memories down to 100, pinned ones first and then the most recently updated (`memoriesOmitted` = number left out; absent when none); (5b) the `text` of queued follow-ups cut to 2,000 and then 200 characters (`queuedItems[].textTrimmed`), the items themselves stay listed so they can still be withdrawn; (6) every card including running ones, finished first and then oldest first: worker chat down to the newest 12 and then 2 entries (`todos[].buildChatTrimmed`), timeline down to the newest 12 and then 6 entries (`todos[].timelineOmitted` = number of older entries left out; absent when none), and the plan cut to 50,000 UTF-8 bytes (`todos[].planTrimmed`); (7) since 0.9.68 the oldest finished cards and then the oldest idle cards in phase `todo` / `queued` / `failed` are first reduced to stubs (`todos[].stubbed: true`, see below), and only when even the stubs do not fit are the oldest finished and then idle cards left out (`todosOmitted` = number left out; absent when none). Before 0.9.68 whole finished cards were left out at this stage, so the 已完成 column shrank as the board grew; (8) last resort, in this order: uploaded agent avatars (data URLs) replaced by the built-in default marker `notion:<role>-<agentId>` and uploaded project avatars by the stand-in `omitted:<projectId>`, which the UI renders as the project monogram (`agents[].avatarOmitted` / `projects[].avatarOmitted: true`); each card's `spec` cut to 4,000 characters (`todos[].specTrimmed: true`); topic conversations down to the newest 5 and then 1 message (`topics[].messagesOmitted`); whole topics left out, archived first and then the least recently active, never the most recently active one (`topicsOmitted` = number left out; absent when none); then the oldest `failed`, `confirm` and `review` cards left out (counted in `todosOmitted`). Cards in `building`, `reviewing` or `merging` are never left out; the most recently active topic is trimmed last. A trimmed snapshot carries `snapshotTrimmed: true`; the top-level flags `snapshotTrimmed`, `todosOmitted`, `topicsOmitted` and `memoriesOmitted` are optional and absent on an untrimmed snapshot, so older clients are unaffected. `counts` is computed before trimming and always describes the full board. A value between 1,500,000 and 2,000,000 bytes after every stage is still returned. Above 2,000,000 bytes the call does not fail (a write that already succeeded must not be reported as an error): it returns a contract-valid degraded snapshot with `snapshotOverflow: true` and `overflowBytes` (size of the fully trimmed board). In it `settings`, `concurrency`, `counts`, `runtime`, `schedules` and `quotaProviders` are real, `memories` is an empty array (`memoriesOmitted` gives the real number), uploaded avatars are replaced by their stand-ins, and every topic and todo is reduced to a stub with `stub: true` so the board can still list them: a topic stub keeps `id`, `title`, `archived`, `updatedAt`; a todo stub keeps `id`, `number`, `title`, `phase`, `gateOwner`, `gateKind`, `updatedAt`, `projectId`, `topicId`. All other collections on a stub are present but empty (`messages`, `queuedItems`, `brief`; `tags`, `diffs`, `buildChat`, `timeline`, `fallbackHistory`, `evidence`, `question`) so existing clients do not break on a missing field. If the base of the degraded snapshot is itself over 1,500,000 bytes, `agents` and `projects` are not emptied but reduced to stubs with `stub: true` (an agent stub keeps `id`, `name`, `role`; a project stub keeps `id`, `name`, `monogram`, `accent`; stub ids are cut to 120 characters) so the lists still point at the entry to fix, and `schedules` and `quotaProviders` are emptied; stubs are added newest first for as long as they fit, and `todosOmitted` / `topicsOmitted` count any that did not. After the stubs are added the size is checked once more against 2,000,000 bytes: if it is still over, `agents` and `projects` are emptied, and if even that is over, only `settings`, `concurrency` and `counts` are kept (each reduced to its values of at most 1,000 bytes; all other collections empty, `runtime` an empty object), so the returned value never exceeds the host limit. The board shows `todosOmitted` under the 已完成 column as 还有 N 张卡未加载（超出快照预算） (`data-testid="lane-todos-omitted"`); it does not show a notice for `snapshotOverflow` yet. The limits equal the `maxLength` already declared on the UI RPC inputs; `configure_agent`, `configure_chief` and `configure_project` now declare them too. Only a value that changes is checked, so saving an entry whose older stored value is over-long neither fails nor rewrites it.
- Rows stored before these limits are shortened in `get-state` only: `agents[].modelConfigs` and the flat config fields (`agents[].modelConfigsTrimmed: true`), `settings.defaultCloneRoot` (`settings.defaultCloneRootTrimmed: true`) and project text (`projects[].trimmedFields` lists the shortened fields). `update-project` treats a value equal to the shortened board form of an over-long stored field as "unchanged", so saving the project form from such a board keeps the full stored text; the test gate always runs the stored command.
- Saving an agent never replaces a longer stored model config string by its shortened board form: in `db.upsertAgent`, a flat config field or a `modelConfigs[]` string field (configs are matched by `id`) whose incoming value equals the shortened view of an over-long stored value keeps the stored text. A field is written only when it changes to a different value, which is then checked against its limit.
- Tags, topic titles, agent references and schedule fields: a todo keeps at most 8 tags of at most 40 characters each (`db.createTodo`, `db.updateTodo`; longer tags are shortened, and `createTodoInput.tags.items` declares `maxLength` 40); a topic `title` is stored within 160 characters (`db.createTopic`, `db.updateTopic`; `rename_topic` declares `maxLength` 160). Older rows are shortened in `get-state` only (`todos[].tagsTrimmed`, `topics[].titleTrimmed`). A project's `ownerAgentId` / `reviewerAgentId` over 120 characters, and a schedule's `runAtIso` over 80 or `agentId` over 120 characters, are refused with `<field> 超过 <N> 字符上限` and nothing is stored; `configure_project`, `create_schedule` and `update_schedule` declare the same `maxLength`. An unchanged stored value is not re-checked.
- A refused write stores nothing. `configure_chief` / `quick-configure-chief` validate the settings part and the agent part first (`db.updateSettings` and `db.upsertAgent` with `dryRun`) and only then write either, so a refused field never leaves the other half saved.
- Todo and memory id fields are used as given and refused when over 120 characters (`<field> 超过 120 字符上限`, nothing stored): `agentId`, `reviewerId`, `topicId` in `db.createTodo` (checked before a card number or a topic is created) and a new memory `id` or changed `scopeId` in `db.upsertMemory`; `create_todo` (`topic_id`, `agent_id`) and `manage_memory` (`memory_id`, `scope_id`) declare `maxLength` 120. Rows stored before the limit are shortened to 120 characters in `get-state` only, with `todos[].trimmedFields` / `memories[].trimmedFields` listing the shortened fields. A shortened memory `id` sent back by a client resolves to the stored row for update and delete, and a shortened `scopeId` sent back keeps the stored value.
- Agent ids and the Chief agent id are bounded at 120 characters. `db.upsertAgent` refuses a new agent `id` over 120 (`configure_agent` declares `maxLength` 120 on `agent_id`); `db.updateTodo` refuses a changed `agentId` / `reviewerId` over 120; `db.updateSettings` refuses a changed `chiefAgentId` over 120 before anything is written (`configure_chief` declares `maxLength` 120 on `chief_agent_id`). Rows stored before the limit are shortened in `get-state` only: `agents[].id` (with `agents[].trimmedFields` containing `id`, and the agent's `cooldowns[].agentId` shortened the same way) and `settings.chiefAgentId` (`settings.chiefAgentIdTrimmed: true`). The shortened agent id resolves to the stored row for save and delete, and a shortened `chiefAgentId`, `agentId` or `reviewerId` sent back keeps the stored value. An exact stored id passed by internal callers still addresses its row.
- An over-long id that addresses an agent row already stored (written before the limit) can still be assigned (since 0.9.22): when `db.updateTodo` writes `agentId` / `reviewerId` or `db.updateSettings` writes `chiefAgentId`, a value over 120 that is the full stored id, or its shortened board form, is written as the stored id; any other value over 120 is still refused. `start-build`, the concurrency queue and schedules resolve a shortened agent id to its stored row before picking the agent. `delete-agent` resolves the id first and compares the stored id with `settings.chiefAgentId`; when the deleted agent was the Chief, the binding moves to a remaining Chief-role agent, else to the first remaining agent, else to `''`. `clear-agent-cooldowns` resolves the shortened id before deleting the cooldown records. No stored data changes shape.
- An agent's `systemPrompt` is written (cut to 20,000 characters) only when it changes. A save that omits it, sends it back unchanged, or sends the shortened form the board shows for an older over-long prompt keeps the stored text; `get-state` shortens such a prompt in the view only (`agents[].systemPromptTrimmed: true`), and workers keep receiving the full stored prompt.
- Other stored text caps: `settings.charter` 20,000 characters (`db.updateSettings`; `configure_chief` declares the same `maxLength`), `topics.last_error` 2,000 characters (`db.updateTopic`), topic message `text` 20,000 characters (`db.addTopicMessage`). Text over a cap keeps its head and ends with `…`.
- Caps apply only to a field the write actually carries. `db.updateTodo`, `db.updateTopic` and `db.updateSettings` never shorten a field that is not in the patch, so a row written before the caps keeps its full `spec`, `plan`, `title`, `buildChat`, `lastError` or `charter` through unrelated updates (timeline entries, phase changes, renames); agents keep receiving the full stored text and only the board view is shortened.
- Stored todo text is capped in `db.updateTodo`, the only write path for these fields (`src/server/diff-budget.mjs`): `lastError` 2,000 characters; each timeline `event` 600 characters and the newest 80 entries; `plan` 50,000 UTF-8 bytes; `buildChat` the newest 24 entries, each `text` 4,000 characters. `spec` 20,000 characters and `title` 200 characters, applied in both `db.createTodo` and `db.updateTodo`; the MCP tools `create_todo` / `update_todo` declare the same `maxLength` (the UI RPC `create-todo` keeps its stricter 12,000-character `spec` limit). A `spec` over the cap keeps its head, so a `User Decision` line appended by `answer_question` to an already full spec is cut; the answer still reaches the worker in the resume message and stays in the timeline. Text over a cap keeps its head and ends with `…`; when a `lastError`, timeline event or `spec` is cut, one host log line (`log.warn`) records `todoId`, the original `length` and `head` (its first 2,000 characters), never the whole text; a log sink that throws does not fail the write. No schema or version change: existing rows are not migrated, a field is brought within its cap only when a later write carries that field, and until then `get-state` shortens an oversized stored `lastError` in the returned value only and marks it `todos[].lastErrorTrimmed: true`. The same applies to an oversized stored `spec` (`todos[].specTrimmed: true`); workers still receive the full stored text.
- Session Trace (`get-session-trace`) reads `ctx.host.sessions.get/messages` only for sessions recorded on this profile's topics (`chief_session_id`) or todos (`build_session_id`, `review_session_id`); tool calls are paired with results by `tool_call_id`, long payloads are clipped server-side, and nothing is persisted.
- Chief busy-poll guard: a Chief shell tool call with `sleep >= 20s` or a direct read of `ekko-todo.sqlite` / plugin-data is warned once per turn and stopped on the second occurrence; unfinished todos of the topic are auto-watched so the Chief is woken on change.
- Chief loop guard: within one Chief turn, the same sentence (>= 4 characters, whitespace ignored) written 3 times in a row with no real tool call in between (6 times in a row regardless), or 5 `tool_describe` calls in a row with no real tool call in between (`tool_search` is not a real call), stops the host run. The topic gets `isRunning=false` / `activeRunId=''` and one `kind: "system"` message whose `text` and `progressNotice` start with `检测到重复输出，已中止本轮`; queued topic messages are then drained. Late tool events of the stopped run are ignored until that session reports a run start or end. No contract field is added; the limits live in `src/shared/loop-guard.mjs` (`REPEAT_NARRATION_LIMIT`, `REPEAT_NARRATION_HARD_LIMIT`, `DESCRIBE_ONLY_LIMIT`, `MIN_NARRATION_CHARS`) and are not configurable. The client applies the same rule to the live stream and shows `检测到重复输出，正在中止本轮…` until the stored message arrives.
- `read-local-file` (read-only) serves host files to the chat preview: `mode` meta | text (first 400 KB) | bytes (base64, ≤1,000,000 bytes per chunk from `offset`, `eof` marks the end). It resolves symlinks, refuses credential/secret/database files and paths outside the allowed roots (`src/server/local-file.mjs`), and caps files at 60 MB. The client (`src/client/local-files.js`) caches Blob URLs, limits reads to two in flight and never puts a host path into an `<img src>`.

## Client interaction rules (client only, Todo #100)

只在页面内存里，不发送、不存储；没有新增或修改契约模型、RPC、工具或数据库列。规则集中在 `src/client/interaction.js`，界面只调用它们。

- **全页忙锁**（`createRpcGate`）：占锁的 RPC 在途时再点别的按钮，不再静默丢弃。同一动作重复点击（RPC 名与入参相同）只提示「正在处理上一个操作，请稍候」并丢弃；不同动作提示「…完成后继续执行刚才的操作」，等当前调用结束后执行，多次点击只保留最后一个。`callRpc(..., { free: true })` 仍不占锁（0.9.65 的发送路径不变）；抽屉与弹窗内自带锁的按钮不变。
- **全局快捷键**（`resolveGlobalShortcut`）：命令修饰键按平台取——macOS 只认 ⌘，其他平台只认 Ctrl。输入态（`input` / `textarea` / `select` / `contenteditable` 及其内部节点 / `role=textbox|searchbox|combobox`）下只保留 ⌘K、⌘P、⌘J、⌘N、⌘,、⌘/、⌘B、⌘⌥B、⌘⇧↵；⌘[、⌥↑/⌥↓、⌘⌥S、⌘⌥↵、N、Esc 一律不触发。
- **命令面板**：cmdk 的 Ctrl+J/K/N/P 列表导航只在 macOS 开启（那里 Ctrl 不是全局修饰键）；其他平台关闭，Ctrl+K/P/J/N 只作全局快捷键，方向键导航不受影响。
- **二次确认**（`ConfirmDialog` + `dangerCopy`）：删除 Agent、记忆、定时规则、话题、自定义配额源都先弹确认，写明对象名称与后果；执行中按钮禁用，失败原因留在弹窗内可重试。卡片与项目原有的确认条不变。
- **⌘⌥↵**（`quickConfirmPlan`）：方案待确认 → 批准方案；非代码交付物待验收 → 验收（`complete`）；待合并 → 先确认「合并 #N 到 <默认分支>」（部署卡为「批准放行部署 #N」）再发 `approve_merge`；待办 → 开工。成功提示按实际动作区分。
- **如实反馈**：复制只在浏览器确认写入后显示成功，否则提示失败；分支、提交记录、模型目录读取失败时显示原因与「重试」，不再显示成空列表；新建任务等服务端创建成功后才关闭弹窗，失败时保留已填内容并在弹窗内显示原因。
