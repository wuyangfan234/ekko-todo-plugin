# Ekko ToDo Data Contracts & Persistence

Authoritative field schemas live in `contracts/plugin.json`. This document summarizes runtime storage, lifecycle guarantees, and host boundaries.

## Storage & Isolation

- All durable state is stored in `ekko-todo.sqlite` inside the host-managed `ctx.paths.dataDir` (retained across plugin upgrades and reloads; never inside the package install directory).
- SQLite runs in `WAL` mode with `foreign_keys = ON` and `busy_timeout = 5000`.
- Every entity (`projects`, `agents`, `config_cooldowns`, `memories`, `topics`, `topic_messages`, `topic_queue`, `todo_queue`, `todos`, `todo_counters`, `todo_watches`, `schedules`, `quota_providers`, `settings`) is strictly scoped by `(user_id, profile)` derived from `run.identity` (never trusted from browser input).
- Isolated Git worktrees are created under `<dataDir>/worktrees/`, keeping the user's main repository checkout clean at all times. Project Workspace file/branch/history browsing uses pure read-only Git object commands (`git for-each-ref`, `git ls-tree`, `git show`, `git log`) with zero checkout or working-tree mutations.
- Scheduled task runs (`schedules`, max 50 per profile) evaluate wall-clock timezones via `Intl.DateTimeFormat`, never backfill missed cycles, skip closed/unassigned todos with recorded reasons, override stale runs on next tick, and can be managed by both UI and Chief MCP tools (`list_schedules`, `create_schedule`, `update_schedule`, `delete_schedule`).
- Quota & Token Hub credentials (`quota_providers.secret_value`) are stored server-side only and strictly masked (`hasSecret`, `secretPreview`) in every client snapshot; independent per-provider detection runs natively inside Ekko ToDo via official vendor APIs and built-in local credential/client discovery (Kimi Code, Grok, DeepSeek, Antigravity local language server, Codex, Claude, OpenRouter, Custom balance APIs) with zero dependency on external CodexBar CLI or Magpie. Native token usage records persist in `usage_records`.

## State Machine, Model Failover, Memories & Idempotent Wakes

- Todo lifecycle transitions (`todo`, `queued`, `confirm`, `building`, `reviewing`, `merging`, `review`, `failed`, `done`, `closed`) are validated by an XState v5 statechart (`src/server/state-machine.mjs`). When concurrency slots are full, new builds enter `queued` and automatically start via `drainQueuedTodos()` when a slot frees.
- Chief strict orchestration (`settings.chiefStrictOrchestration`, default `true`) physically isolates Chief sessions in `<dataDir>/chief-workspace`, provides read-only `inspect_project_repo` (MCP tool #27), monitors direct mutating tool calls, and audits registered project repo fingerprints pre/post-turn.
- `todo-action` `delete` removes a card on user request: it refuses while `merging`, stops live build/review sessions, removes the plugin worktree, deletes the task branch only when already merged (`git branch -d`, unmerged branches stay), and drops its watches, wake log and schedules. Todo numbers come from `todo_counters` (per-project high-water mark) and are never reused, so a new card can never pick up an old branch.
- Mid-run Chief messages and automated task wakes arriving while Chief is busy are persisted in `topic_queue` and drained in strict FIFO order (coalescing consecutive wakes) so turns never collide and multi-todo wakes are never lost.
- Isolated Git worktrees auto-symlink gitignored dependency paths (`.venv`, `node_modules`, `.env`) for out-of-the-box test execution and safely unlink recorded symlinks before worktree removal.
- Worktree capture first bounds previews to 20 files, 180 lines per file, 2,000 characters per line, 20,000 characters per file, and 200,000 UTF-8 bytes for the serialized `diffs` array. The original character count survives the subsequent shared clamp, and budget-exhausted tail entries retain minimal `path`/`additions`/`deletions` statistics. These capture bounds feed, rather than replace, the v0.9.8 `clampDiffs` and `fitSnapshotBudget` protections below.
- Each Agent stores up to 8 ordered `modelConfigs` (primary + fallbacks), an `autoFallback` toggle, and a `maxTurns` budget (`0` = unrestricted / inherit engine native turn cap such as Hermes 500, or explicit `1–2000`). On genuine model/provider service faults (quota, 429/529, 401/403, 5xx, network timeout, incompatible parameters, and since 0.9.46 an empty model response), `src/server/failover.mjs` records a 1-hour cooldown in `config_cooldowns` and automatically reruns on the next healthy fallback configuration.
- Failure categories (`classifyModelFailure`, stored in `todos.fallbackHistory[].category` and `config_cooldowns.category`). Not switchable: `non_model` (abort / cancel / stopped by user, merge conflict, uncommitted changes, worktree, test gate, `rc=1…9`, and since 0.9.46 the bare fallback wording `执行会话异常结束` / `审查会话异常结束`; checked first, so such a text never switches even when it also names a model fault) and `unknown` (empty text, or nothing matched). Switchable: `quota_spent`, `rate_limited`, `auth_failed`, `model_unavailable`, `upstream_fault`, `network_cutoff`, `incompatible_request`, and since 0.9.46 `empty_output` (label `模型返回空响应`: `response.output is empty`, `empty after stream backfill`, `Invalid API response`, `no content`, `no visible content`, `empty response`, `empty output|message|completion`, `Reasoning-only response`, `无输出`, `空响应`). The first two `empty_output` wordings are checked before the other switchable categories, the rest after them, so `Invalid API response …: 429` stays `rate_limited`. No stored value is migrated; rows written before 0.9.46 keep their category.
- Failed build run (since 0.9.46). The cause is the `error` / `message` of the host `chat.run.failed` event (a string, or an object with `message` / `error` / `detail`). When that is empty or only `执行会话异常结束`: (1) an event with `interrupted: true` is recorded as `运行被中断，宿主没有给出错误信息（会话 <id>…）`, category `non_model`; (2) otherwise `host.sessions.get(sessionId)` is read for at most 3 s and the first non-empty of `lastError`, `last_error`, `error`, `errorMessage`, `error_message`, `failureReason`, `failure_reason` (on `session`, then on the answer itself) is the cause; (3) otherwise, when the transcript was read, is not empty and holds no assistant text after its last user message, the cause is an empty model response (`empty_output`, switchable); (4) otherwise the category is `unknown` and the text is `未能取到模型侧原始错误（会话 <id>，配置 <config label>，宿主事件 code=… stop_reason=…）` (the last part only when the event carried `code` or `stop_reason`, each cut to 80 characters). `todos.lastError` is the cause cut to 400 characters plus `…`, prefixed `模型服务异常（<category label>）：` when the category is switchable and left as is otherwise; the timeline gets `构建失败：<lastError>`. A switchable fault with `autoFallback` on and no config to switch to (none configured, or all inside the cooldown) additionally writes the timeline line `模型 <config label> 服务异常（<category label>），但没有可用备选配置…` (actor `failover`) and the card fails. The wording of a failed review run (`审查会话异常结束`) and of a failed Chief run (`总管会话异常中断`) without an event error is unchanged.
- Idle build round (since 0.9.47). `todos.evidence` (a JSON object, shallow-merged on every write; no column and no migration) gains four optional keys. `roundBaseSha` (string, full sha, default `''`) and `roundBaseTree` (string, tree sha, default `''`) are written by every build dispatch: HEAD of the worktree and the tree of its files on disk (uncommitted and untracked included, bootstrap symlinks excluded) at that moment; both are `''` when they could not be read after two attempts (timeline `本轮无法确定基线，跳过产出校验`), and an instruction the host refused as "already running" leaves the values of the running turn in place. `gateSkipped` (string: `''`, `'no-new-commit'` or `'no-snapshot'`) is reset to `''` by every dispatch, which also resets `testRc` to `-1` and `testSummary` to `''` (the result of the round before is not shown while the next round is building). `idleRetries` (integer, absent = 0) counts the automatic reruns of the card after an idle round and is never reset. When a build turn ends as completed, before the test gate: the snapshot's `headSha` and `worktreeTreeSha` (both new in the result of `captureWorktreeSnapshot`) are compared with the baseline. Both equal = idle round. A moved HEAD (an empty commit, or a commit that is reverted by a later commit, included) or a changed tree (uncommitted edits included) = output, and the settle is what it was before. Not judged: planning rounds (`withPlan`; nothing is written), a missing snapshot (the worktree is gone or the snapshot failed; timeline `取不到工作树快照，跳过产出校验`; when the project has a test command it is not run, `evidence` gets `gateSkipped: 'no-snapshot'`, `testRc: -1`, `testSummary: ''`, and the card reaches the review gate with `gateOwner: 'human'`), a missing baseline, e.g. a card dispatched before 0.9.47 (timeline `本轮没有可用的开工基线，跳过产出校验`). `kind: 'deploy'` cards are judged like any other card. A round that ended with the host event `chat.run.stopped` (the settle input `stopped`, default `false`) is compared too: with output it settles as before; without output it is never rerun, the card goes to `failed` with `lastError` `本轮被停止，没有产出（HEAD 仍为 <12-char sha>）` (plus `，未提交的改动与开工时相同` inside the brackets when the files on disk differ from HEAD), `gateSkipped: 'no-new-commit'`, no `config_cooldowns` row, no `fallbackHistory` entry, `idleRetries` unchanged, and the Chief is not woken. An idle round never runs the test gate. With `autoFallback` on, `idleRetries` below 1 and a config to switch to, the card stays `building` and is dispatched again in a new session on that config: `idleRetries` + 1, a `fallbackHistory` entry and a `config_cooldowns` row with category `idle_build` (label `构建会话空转（无产出）`; this value is produced by the orchestrator only, `classifyModelFailure` never returns it). The `config_cooldowns` row is written only when the card really switches: with nothing to switch to, the config that idled is not cooled down. When the rerun cannot be started the card goes to `failed`, `lastError` is the idle text plus `；自动重跑未能启动：<reason, at most 300 characters>`, and `idleRetries` is set back to its value before the attempt (the `fallbackHistory` entry and the cooldown stay). Otherwise the card goes to `failed` (`gateKind: 'failed'`, `gateOwner: 'human'`), `lastError` is `本轮没有产生任何提交（HEAD 仍为 <12-char sha>），任务未推进`, or `有改动未提交，且 HEAD 未前进（<12-char sha>）` when the files on disk differ from HEAD, and `evidence` gets `gateSkipped: 'no-new-commit'`, `testRc: -1`, `testSummary: ''` (a result left by an earlier round is cleared, so the Chief merge gate cannot read it as passing).
- Persistent memories (`chief`, `project`, `agent` scopes), standing `Charter`, and repository `AGENTS.md`/`CLAUDE.md` files are injected cleanly with bounded budgets.
- Chief super-admin MCP mutations (`configure_chief`, `configure_agent`, `delete_agent`, `configure_project`, `import_github_project`, `manage_memory`) check `settings.chiefAuthority` before mutating state.
- Automated Chief wakes are deduplicated by `wake_log(wake_key)` (`wake:<todoId>:<revision>:<phase>:<reason>`, and `wake:<todoId>:merged` for terminal merges) so crash recovery, double-clicks, or duplicate events never trigger duplicate Chief instructions.
- A watch that cannot wake a Chief is recorded, never skipped. A watching topic without a Chief session (`chiefSessionId` empty) still gets the `关注的任务有进展` system message, with `（本话题没有总管会话，未唤醒总管）` at the end of `progressNotice`; the card timeline gets `进展已记入话题「<title>」，但该话题没有总管会话，未唤醒总管`; no host run is started. A watching topic that is archived or deleted gets no message; the card timeline gets `进展通知未送达：话题「<title>」已归档` or `进展通知未送达：话题 <topicId> 已不存在`. Both cases write a host log warning and their own `wake_log` row, keyed `<wake key>:unattended:<topicId>` or `<wake key>:undelivered:<topicId>`. These keys include the topic id, so they do not take the plain key that the one Chief wake per event uses. `wake_log` has no new column; rows written by older versions stay valid, and an older version ignores the new rows.
- `create-todo` / `create_todo` without `topicId` choose the topic in this order: (1) the topic whose `chiefSessionId` equals the caller's `run.identity.sessionId`, same account and profile, not archived; (1a) since 0.9.45, the topic whose Chief session has just started the create-todo tool (item after next); (2) since 0.9.44, the topic whose Chief session has a run under way (next item); (3) the non-archived topic of the account and profile with a Chief session that was updated last (`updatedAt`, sorted explicitly; pinning has no effect), whatever its project; (4) the first non-archived topic of the project without a Chief session, in sidebar order; (5) a new topic for the project, titled with the first 32 characters of the card title, `autopilot: false`. In cases (4) and (5) a system message starting with `无人值守话题：#<number>` is stored in the topic and a warning is logged. The card is watched by the chosen topic in every case. A given `topicId` is used as it is. In case (3), when the topic has a project and it is not the card's project, the card timeline gets `卡片挂在话题「<title>」（属于项目 <name>），与建卡项目 <name> 不同`; a topic without a project gets no such line. The `create_todo` tool answers `data.topicId` and `data.topicResolvedBy`: `explicit` (given `topicId`), `caller-session` (1), `caller-tool` (1a, since 0.9.45), `active-run` (2), `chief-topic` (3) or `unattended` (4, 5); for `unattended` its `content` also carries `未能识别调用方话题，卡片挂在没有总管会话的话题 <topicId>，进展不会唤醒总管。请显式传 topic_id 重新指定。`, and for `active-run` chosen among several running Chiefs (since 0.9.45) `当前有 N 个总管会话在运行，无法确定建卡归属，请显式传 topic_id。卡片暂挂在话题 <topicId>（取最近开始的总管运行），可能不是你的话题。`. The `create-todo` RPC output is unchanged (`stateSnapshot`). History: before v0.9.38 step (1) did not exist and the first topic of the project was taken whether or not it had a Chief session, a new topic being created with `autopilot: true` and no message. From v0.9.38 to v0.9.43 step (2) did not exist and step (3) only looked at topics of the card's project in sidebar order (pinned first). In v0.9.44 step (1a) did not exist, so with two Chiefs running the card went to the one that started last, whoever was calling. Nothing stored changes with 0.9.44 or 0.9.45: topics and cards created earlier keep their topic and project.
- Running Chief sessions (since 0.9.44), in memory only: `activeChiefRuns`, `sessionId → { startedAt, lastSeenAt }`. Written when a `chat.run.started` event names a session that is some topic's `chiefSessionId` (`startedAt` reset), and refreshed by `chat.tool.started` / `chat.tool.completed` / `chat.tool.failed` of such a session (`startedAt` kept; set when the session was not recorded yet, which covers a `run.started` that was never delivered or arrived before a plugin reload). Removed by `chat.run.completed` / `chat.run.failed` / `chat.run.stopped`. Build, review and plain chat sessions are never recorded; `chat.run.queued` does not record. An entry counts for step (2) only when its topic belongs to the calling account and profile, is not archived, is still `isRunning`, and the entry was seen in the last 6 hours; among several the one with the latest `startedAt` wins. That is a guess, not an identification of the caller: the card timeline gets `建单未指定话题：按活跃总管运行推断，挂到话题「<title>」（N 个总管在跑，无法确定调用方，取最近开始的）` (v0.9.44 wrote `（同时有 N 个总管会话在运行，取最近开始的一个）`; lines already stored keep that text) and the `create_todo` tool asks for `topic_id` in its `content`. At most 200 entries are kept. If the host delivers no event at all for a run, step (2) finds nothing and step (3) applies; a card reaches an unattended topic only when the account has no non-archived topic with a Chief session.
- Calling Chief session (since 0.9.45), in memory only: `chiefToolCalls`, `sessionId → { toolName, at }`, the tool a Chief session started last. Written by a `chat.tool.started` event that names a tool and a session that is some topic's `chiefSessionId` (same condition as `activeChiefRuns`; build, review and plain chat sessions are never recorded). The tool name is read from `data.name`, `data.tool`, `data.toolName`, `payload.tool_name`, `payload.name`, `summary.tool_name` or `data.summary.tool_name`, first non-empty; the event arguments are not used. A tool is a create-todo tool when its name matches `/create[-_]?utodo|create[-_]?todo/i` anywhere, so `mcp__ekko_todo__ekko_todo__create_utodo`, `…create_todo`, a bare `create_utodo`, `create-todo` and `createTodo` all count, and `update_utodo`, `list_utodos`, `tool_call`, `terminal` do not. A later tool replaces the entry, except that a create-todo entry inside its 120 seconds is not replaced by a tool that is not one (tools of one batch are announced one after another). The entry is removed by `chat.tool.completed` / `chat.tool.failed` of that session carrying the same tool name or none, by `chat.run.started`, `chat.run.completed`, `chat.run.failed`, `chat.run.stopped`, and when read after 120 seconds. For step (1a) an entry counts when it is a create-todo tool, `at` is at most 120 seconds old, and its topic belongs to the calling account and profile, is not archived and is still `isRunning`; among several the latest `at` wins. The card timeline gets `建单未指定话题：按调用中的工具定位到话题「<title>」`. At most 200 entries are kept. Limits: a host or agent that announces a wrapper instead of the tool (`tool_call`) or announces nothing is not recognised and step (2) applies; a tool of another server whose name contains `create_todo` is recognised too.
- Topic project (since 0.9.44). `create-topic` without `projectId` stores `''` (no project); the page sends a project only when the topic is created from a project page, never the first project of the list or the project of the open topic. `update-topic` with `projectId: ''` detaches a topic; a non-empty id must be a project of the account or the call fails with `项目不存在：<id>`. The topic menu has `改挂项目` for this. No stored topic is changed by the upgrade.
- The sidebar shows `无人值守` on a topic that has watched cards (`watchedTodoIds` not empty), an empty `chiefSessionId` and `isRunning: false`. It is computed from the snapshot; no field was added. The tag goes away when the topic gets a Chief session (the first message sent in it) or its last watch ends.
- Topic-level human decisions (`brief.waitingOnYou`, `brief.waitingRecommendation`, `brief.waitingOptions`) set via `update_topic_brief` or topic-scoped `ask_user` are surfaced directly in the Kanban `待你处理` column with Chief's recommendation pre-filled by default, and cleared via `clear-topic-waiting` with structured `【批复确认】` dispatch back to Chief.
- Avatar storage (`agents.avatar`, `projects.avatar`) enforces strict dual client+server validation (`notion:<seed>` alphanumeric seeds, legacy `preset:*` IDs, or `data:image/(png|jpeg|webp);base64,...` capped at 128 KB; raw SVGs are rejected to prevent XSS).
- Web-UI session isolation (`settings.sessionIsolationMode`: `category` / `hidden` / `default`, `settings.sessionCategoryName`) organizes all Ekko ToDo sessions via native Studio `/api/studio/session-categories`, `/api/studio/sessions/:id/category`, and archive APIs without modifying host files.
- Profile-scoped GitHub Personal Access Tokens (`settings.github_pat`) are never serialized to client snapshots or persisted into repository `.git/config` files; private clones pass ephemeral per-command Authorization headers only.
- Chat file attachments follow Hermes-WebUI's 50 MB upload & multimodal content-block specification (`[{ type: 'text' }, { type: 'image' | 'file', name, path, media_type }]`) with strict path-root containment inside host `~/.hermes-web-ui/upload` or `<dataDir>/uploads`.

## Host Integration Boundaries

- Multi-engine sessions run through `ctx.host.sessions.*` (`create`, `setWorkspace`, `setModel`, `run`, `stop`, `messages`, `connect`) bound to the caller's authenticated Studio profile.
- Live engine model catalogs and supported `reasoningEfforts` are queried dynamically via `ctx.host.agents.models(id)` and `ctx.host.models.list()`.
- Background reconciliation runs inside `apply(ctx)` via `ctx.scheduler.every('reconcile-loop', intervalMs, 'reconcile')` and `ctx.events.on('chat.*', ...)`, never inside 120-second RPC handlers.
- Follow-up syncs after a Chief turn ends run in the `settle` action via `ctx.scheduler.every('settle-loop', 2000, 'settle')`. Event and RPC callbacks only record which topic needs it (in memory, at most 200 topics); they start no timer, because a callback's `run.host` is cancelled once the callback returns. Output `settleResult`: `ok` (always true), `pending` (topics still waiting, 0 when none), `settled` (topics changed by this pass). Schedule per topic: first pass about 1s after the turn was seen finished, then up to 3 retries about 2s apart; it stops early when a pass adds nothing and the host tail is unchanged, or when a new turn has started. No stored data changes shape; pending entries are lost on reload and the reconcile loop then covers the 8 most recent topics.
- Chief transcript sync reads the newest 80 host rows and pages back with `offset` (80 rows per page, at most 12 pages) until a page contains a host message the topic already holds. `topic_messages.host_message_id` is the only idempotency key: two host messages with the same text are two rows. Matching by text and time (within 120s) is used only against a stored Chief message whose `host_message_id` is empty.
- `topic_messages` has a unique index `idx_topic_msgs_host` on `(topic_id, host_message_id)` for rows where `host_message_id` is not empty; inserting a second row for the same pair is skipped and reported as not added. Migration (runs once, when the index is missing): rows that repeat a `(topic_id, host_message_id)` pair are deleted, keeping the row stored first; rows with an empty `host_message_id` are not touched. If the index cannot be created the plugin still loads and the insert checks for an existing row instead. An older plugin version can open the migrated file; the index only makes its duplicate insert fail for that one message.
- Sending a message (since 0.9.42). `send-topic-message` takes an optional `clientNonce`: 1-64 characters from `A-Z a-z 0-9 _ . : -`, made by the page for one press of send. Omitted, empty or with other characters: the message is stored without a nonce and nothing below about nonces applies (behaviour before 0.9.42). Order of work on the server: (1) validate the input and the topic; (2) if this topic already holds the nonce, as a message or as a queued follow-up, store nothing, start nothing and return the current state; (3) if the topic is not known to this process as running, or `interrupt` is true, store the `kind: "human"` message and emit `board.updated` with `reason` `topic.message.accepted:<topicId>`; (4) only then probe the session and the engines and start the Chief. If the topic is known as running the message is not stored as a bubble first: the probe decides, and a busy topic gets a queued follow-up (`topic_queue`, reason `topic.message.queued:<topicId>`). If step (3) stored the bubble and the probe then finds a run started outside the plugin, that bubble row is deleted and the message becomes a queued follow-up with the same nonce. `drainTopicQueue` and `promote-topic-queue-item` also store the bubble and emit `topic.message.accepted:<topicId>` before probing engines.
- Stored fields (since 0.9.42). `topic_messages.client_nonce` and `topic_messages.send_error`, `topic_queue.client_nonce`: `TEXT NOT NULL DEFAULT ''`, added with `ALTER TABLE` on first start; rows stored before keep `''`. Unique index `idx_topic_msgs_nonce` on `(topic_id, client_nonce)` for rows where `client_nonce` is not empty: a second insert for the same pair stores nothing. In `stateSnapshot`, `topics[].messages[].clientNonce`, `topics[].messages[].sendError` and `topics[].queuedItems[].clientNonce` are strings and are present only when not empty, so a snapshot of older data is unchanged. `sendError` is the text of the error the call failed with (the same readable text as `topics[].lastError`), cut to 500 characters. It is written when the Chief could not be started for that message and is never cleared; the message row is kept. `send-topic-message` fails with that error when the launch failed before the call answered; see the time limit below. Unique index `idx_topic_queue_nonce` on `topic_queue(topic_id, client_nonce)` for rows where `client_nonce` is not empty: before it is created, rows sharing a topic and a non-empty nonce are reduced to the earliest (`created_at`, then `rowid`); inserting a second row for the same pair stores nothing.
- Order (since 0.9.42). Topic messages and queued follow-ups are read `ORDER BY created_at ASC, rowid ASC`: two rows with the same millisecond keep the order they were stored in.
- `board.updated` reasons `topic.message.accepted:`, `topic.message.queued:` and `topic.message.failed:` are read by the page at once. Every other reason stays in the page's refresh window (one `get-state` in flight, the next not earlier than 800 ms after the previous one started). The event name, payload shape (`at`, `reason`) and audience are unchanged; `topic.message.accepted` and `topic.message.failed` are new values of `reason`.
- The page (since 0.9.42) draws the user's bubble when send is pressed (`data-send-state="sending"`), keyed by the nonce, and replaces it with the stored message carrying the same `clientNonce` (`stored`, or `failed` when `sendError` is set). A stored message is drawn once per id and once per nonce. A send whose nonce is on a queued follow-up is shown in the queue tray only. Unconfirmed bubbles live in page memory only: after a reload, a reconnect or a topic switch the list is what the server stored. A send that failed before the server stored it keeps its bubble with `未发送：<reason>` until the next send in that topic or a reload; the composer gets the text and files back by the 0.9.27 draft rules. When no topic is selected the bubble appears after `create-topic` answered.
- Time limit of a send (since 0.9.42). `send-topic-message` and `promote-topic-queue-item` wait for the launch (busy probe, engine probe, session, host run) for at most 800 ms, `message-todo` and the `message_todo` tool for at most 1500 ms. Finished inside the limit: the result or the error is returned as before. Not finished: the call returns the current state (`message-todo`: the card), the launch continues, and its outcome is announced with `board.updated`: `topic.run.started:<topicId>` or `topic.message.failed:<topicId>` (with `sendError` written on the message), then `topic.launch.settled:<topicId>`; for a card `todo.message.accepted:<todoId>` at the limit, the usual build events or `todo.message.failed:<todoId>` after it, then `todo.launch.settled:<todoId>`. The limits are not configurable. A failure after the limit is also written to the host log (`warn`).
- `stateSnapshot.topics[].launching` is `true` while a Chief turn is being started for the topic (send, queue drain or promote) and absent otherwise. `topics[].launchingMessageId` is the id of the user message that turn is for; absent for a wake and when nothing is being started. Both are view fields, not stored.
- Repeats (since 0.9.42). A `send-topic-message` call whose `(topicId, clientNonce)` is being handled by an earlier call returns the current state at once. After the busy probe (up to 700 ms) the nonce is looked up again before anything is stored or started. A send that finds its nonce already stored as a message stops there and starts no turn.
- Bubble or queued follow-up, never both (since 0.9.42). When the launch for a queued follow-up fails and the item goes back to `topic_queue` (queue drain attempts 1 and 2, or `promote-topic-queue-item`), the `kind: \"human\"` row stored for that attempt is deleted. When the third drain attempt fails the item leaves the queue and the row stays with `sendError`. Before 0.9.42 the row stayed in both cases.
- Worker instructions (since 0.9.42). `todo-action` `message_todo`, `request_changes`, `answer_question` and `confirm_plan`, and the `message_todo` / `confirm_plan` tools, take one path, in this order: (1) the same instruction (same card, same kind, same text after trimming) accepted less than 60 s ago returns the current card with `duplicate: true` (plus `launchPending: true` while its run is still being started) and appends nothing, starts nothing; this holds also after its run was started. A failed dispatch forgets the instruction, so sending it again goes through. (2) Any other instruction while one is being handled for the card, or while a start of the card is in progress, fails with a message containing `没有发出` and ending in `请稍后再发`; the timeline gets `<label>没有发出：…`, `board.updated` reason `todo.message.failed:<todoId>`, and nothing else is written (an answer is not recorded on the question). (3) The instruction is written on the card (timeline `发送补充指令` / `退回修改：…` / `用户决策：…` / `方案已确认…`). (4) The build session is probed (at most 700 ms); when it is working or holds queued input, the instruction is stored in `todo_queue`, the timeline gets `<label>已排队，本轮结束后自动送达`, reason `todo.message.queued:<todoId>`, the call returns the card with `queued: true` and no run is sent. (5) Otherwise the run is started with the rest of the 1500 ms budget; at the limit the timeline gets `补充指令已接受，正在后台启动（宿主尚未确认）` (other kinds: `指令已接受，…`), reasons `todo.message.accepted:<todoId>` and `todo.launch.pending:<todoId>`, and the card is returned with `launchPending: true`. `duplicate`, `queued` and `launchPending` are return-value flags of the orchestrator and the tools (`data.duplicate`, `data.queued`, `data.starting`); `todo-action` returns `stateSnapshot` as before.
- `startBuild` (since 0.9.42) fails with `…的构建还在启动中，这次操作没有发出，请稍后再试。` while another start of the same card is in progress. Before, it returned the unchanged card and callers reported the instruction as dispatched.
- A host refusal `already running` for an instruction (since 0.9.42) is a failed delivery: `lastError` and the timeline get `指令没有送达：宿主拒绝了这条指令：执行者会话已有运行中的轮次（already running）…`, reason `todo.message.failed:<todoId>`, and the call fails with that text. The phase is not changed. The initial build prompt keeps the old behaviour (re-attach to the running session).
- `todo_queue` (since 0.9.42): `id TEXT PRIMARY KEY`, `todo_id`, `user_id`, `profile`, `kind` (`message` | `changes` | `answer` | `plan`, default `message`), `text` (the prompt sent to the worker, cut to the queued-text limit), `client_nonce` (`''`, reserved), `created_at` (ms). Created on first start; no migration. When a turn of the card's build session ends as completed, the oldest item is removed and sent as the next run before anything else is settled, whatever the phase (`building`, `confirm`, `review`, `failed` …; not while `reviewing` or `merging`), one item per finished turn, in `created_at, rowid` order. The reconcile action does the same when the build session is idle but no turn-end event arrived. When a delivery fails the item stays removed: the timeline gets `排队的指令没有送达，已移出队列：…（<text>）` and an empty `lastError` gets the same note. When a build turn ends as failed, or the card is `done`/`closed`/`cancelled` or has no build session, or the oldest item waited more than 30 minutes while the session kept running, all items are removed, the timeline gets `排队的 N 条指令没有送达，已移出队列（<reason>）：<texts>`, `lastError` gets the note appended, and `board.updated` reason `todo.message.failed:<todoId>` is emitted; they are never sent later. Deleting the card or its project deletes its items.
- Chief context and slash commands (since 0.9.43). The plugin does not compress or run any command itself; the page sends the host's own command text over its live Chief session handle (`ctx.host.sessions.connect(chiefSessionId, …).run('/compress')`) and reads the host's answer from that subscription: `session.command` (`ok`, `action`, `message`; for compress also `beforeTokens`/`afterTokens`; for context `totalTokens`/`contextWindow`/`contextPercent`) and `compression.started` / `compression.completed`. Commands are not sent through `send-topic-message` / `sessions.run` (HTTP): the host answers a command there with neither `run.started` nor `run.queued`, so the HTTP call would wait for its own timeout. The host only dispatches commands for sessions whose source is `cli`, `global_agent`, `workflow` or `group_chat`; for any other source the text would go to the model.
- `get-topic-context` (`topicContextInput` → `topicContextOutput`): `contextWindow` from the host's `GET /api/studio/sessions/context-length` for the session's model/provider (0 when the host did not answer within 3 s), `commandChannel` `ready` / `unsupported` / `unknown` from the session's `source` (`sessions.get`): `cli`/`global_agent`/`workflow`/`group_chat` = ready, `builtin_agent` (Ekko-agent sessions, which the host answers on its own command path; it names the compress action `compact`) and a missing source = unknown, anything else = unsupported, `reason` the Chinese reason when not ready, `compressionThreshold` from `GET /api/hermes/config?section=compression` (only that section is read; a section without a usable value is 0.5 as the host reads it, clamped 0.05–0.95; 0.65 with `thresholdSource: fallback` when the host did not answer within 3 s), `compressingSince` the lock time or 0. Read-only. The capsule (in the composer toolbar, right-aligned before send; percent only when the composer is narrower than 560 px and on phones, where the whole capsule is one 40 px button) is `上下文 <used> / <window> (<percent>%)` against the context window and turns to the warning style at 90 % of the host trigger (`floor(window × compressionThreshold)`); the used tokens are only the host's own context number (`resumed.contextTokens`, `usage.updated.contextTokens`, `compression.completed.contextTokens`, `run.completed.contextTokens` when the turn has no `error`); the `/context` total (input + output) is another measure and only serves as probe and self-check baseline. An automatic compression shows `压缩中 Ns` from the time `compression.started` arrived; `resumed` (not during this page's manual compression) or 120 s without `compression.completed` ends it.
- Manual compression (since 0.9.43), in this order: (1) before every compression the page sends `/context` and waits up to 8 s for `session.command` `action: context` (this also gives the token baseline for step 4, in the host's `/context` unit) — a `run.started`/`run.queued` instead means the host passed the text to the model: the page stops that run (`stop-topic-run`), records `outcome: unsupported` and disables the button; no answer within 8 s is one failed attempt, recorded `outcome: timeout` (`宿主 8 秒内没有回应 /context，本次未压缩，可重试`): the button stays usable and a later `get-topic-context` answer applies again (only a passthrough makes `unsupported` stick until the topic changes); (2) `begin-topic-compress` takes the lock and answers its `lockId`, refused with a Chinese reason when the topic has no Chief session, a compression is already locked, a Chief turn is being started or drained, or the session is busy (busy probe, at most 1.5 s, fail closed); (3) `/compress` is sent and the page waits up to 120 s for `session.command` `action: compress`; (4) with no answer by then it sends `/context` again and counts a drop below 80 % of the step-1 total as success; (5) `record-topic-command` is called with the `lockId`: it releases the lock and writes a `kind: system` message: `上下文已压缩：<before> → <after> tokens`, `上下文没有可压缩的内容，宿主未改动` (host `compressed: false`, passed as the optional `compressed` input), `压缩失败，上下文未变，可重试：<host message>`, `压缩超时，上下文未变，可重试` or `当前大总管会话不支持手动压缩：…`. A `/compress` the host hands to the model is stopped like the probe and recorded `unsupported`. Detach: when the page leaves the session before the answer (topic switch: another session attaches), the command settles as `detached`; nothing is recorded, no system message is written and the lock stays until it expires (the host keeps compressing without the socket). A detach followed by the same session attaching again keeps waiting; the timer firing while detached also settles as `detached`, never `timeout`. Only the topic's `chiefSessionId` is compressed; build and review sessions are never addressed.
- Compression lock (since 0.9.43): in memory only, `topicId → { since, until = since + 135000 }`; it ends with `record-topic-command` for `compress`/`compact` carrying the lock's `lockId` (a record without it or with another one writes its message and leaves the lock), or by itself at `until`, or with a plugin reload (fail open). While it is held no Chief turn starts for the topic: `send-topic-message` stores the message as a queued follow-up (also with `interrupt`), a wake is queued without setting `isRunning`, `drainTopicQueue` waits, and `promote-topic-queue-item` fails with `上下文正在压缩，压缩完成后会自动执行排队消息`. `isRunning` / `activeRunId` are not touched by a compression. Queued items are sent by the reconcile loop after the lock ends. `stateSnapshot.topics[].compressingSince` (Unix ms) is present only while the lock is held; it is a view field, not stored. `board.updated` reasons: `topic.compress.started:<topicId>`, `topic.command.recorded:<topicId>`.
- Slash-command panel (since 0.9.43). A composer whose text up to the caret is `/` or `／` plus up to 24 of `A-Z a-z 0-9 _ -` opens the command panel instead of the @ picker; the two never open together: typing goes through one function that closes the other panel, and the composer's @ button closes the slash panel before it opens the picker. Picking a command re-reads the `/` token at the caret (`resolveSlashPick`); when the caret has left it (Home, arrows, a click) nothing is inserted and the panel closes. Migrated commands: `/status`, `/context`, `/usage`, `/compress`, `/compact`, `/clear`, `/title <新标题>`, `/abort`, `/queue <内容>`, `/steer <指令>`. `/compress`, `/compact` and `/clear` ask for confirmation first; the copy lives in `COMMAND_CONFIRM_COPY` (`src/client/chief-commands.js`). `/clear` is sent as `/clear`: the host clears its current display and keeps the database history; `/clear` with arguments (`--history`) is refused. Enter with the panel open inserts the highlighted command, sends a fully typed command that takes no text, and does nothing when nothing matches (the draft is not sent). A text the host parses as one of its commands (same pattern as the host: `/name` followed by a space, `:`/`：`/`、`/`,`/`，`, CJK text or the end) is never sent as a chat turn: Hermes Agent commands (`/plan`, `/moa`, `/goal`, `/subgoal`, `/skill`, `/bundles`, `/learn`, `/yolo`, `/fork`, `/destroy`, `/reload-mcp`, `/reload-skills`) are refused with `…是 Hermes Agent 专有命令，大总管会话未开放`; the others are checked first (session exists, channel not unsupported, live connection, not compressing, `/compress`/`/compact`/`/clear` only while idle, `/abort`/`/queue`/`/steer` only while running, `/title`/`/queue`/`/steer` need text) and then sent; the answer (or a 15 s timeout) is written by `record-topic-command` as `/<command>：<host message>` or `/<command> 失败：…`. Text starting with `/` that is not a host command (`/tmp/a.log 看一下`) is a normal message. A message with attachments or referenced cards is always a normal message.
- A launch (Chief turn or worker run) that takes more than 3000 ms writes `Slow launch: …` to the host log with `topicId` or `todoId` and `ms`.
- The `settle` action clears `isRunning`/`activeRunId` only when the host reports the session as idle. When the host cannot say, it copies messages and leaves the flag as it is, the same as the reconcile loop.
- Every plugin RPC value must stay under the host's 2,000,000-byte JSON limit. Todo diffs are clamped (`src/server/diff-budget.mjs`: generated/minified files keep stats only; 500 chars/line, 40 KB/file, 160 KB/todo) and `getSnapshot` trims to 1.5 MB by dropping diff bodies (`hunkOmitted`) that the drawer re-loads through `get-todo-diffs`.
- Snapshot trimming never deletes stored data; it only shortens the `stateSnapshot` value, and each stage stops as soon as the value fits 1,500,000 bytes. Order: (1) diff bodies, finished todos first (`diffs[].hunkOmitted`); (2) worker chat of finished todos down to the newest 12 entries (`todos[].buildChatTrimmed`); (3) older topic messages, archived topics first and then the least recently active, keeping the newest 60 and then 20 per topic (`topics[].messagesOmitted` = number of older messages left out; absent when none); (4) worker chat of finished todos down to the newest 2 entries, oldest todos first; (5) memories down to 100, pinned ones first and then the most recently updated (`memoriesOmitted` = number left out; absent when none); (5b) the `text` of queued follow-ups cut to 2,000 and then 200 characters (`queuedItems[].textTrimmed`), the items themselves stay listed so they can still be withdrawn; (6) every card including running ones, finished first and then oldest first: worker chat down to the newest 12 and then 2 entries (`todos[].buildChatTrimmed`), timeline down to the newest 12 and then 6 entries (`todos[].timelineOmitted` = number of older entries left out; absent when none), and the plan cut to 50,000 UTF-8 bytes (`todos[].planTrimmed`); (7) the oldest finished cards themselves, then the oldest idle cards in phase `todo` / `queued` / `failed` (`todosOmitted` = number left out; absent when none); (8) last resort, in this order: uploaded agent avatars (data URLs) replaced by the built-in default marker `notion:<role>-<agentId>` and uploaded project avatars by the stand-in `omitted:<projectId>`, which the UI renders as the project monogram (`agents[].avatarOmitted` / `projects[].avatarOmitted: true`); each card's `spec` cut to 4,000 characters (`todos[].specTrimmed: true`); topic conversations down to the newest 5 and then 1 message (`topics[].messagesOmitted`); whole topics left out, archived first and then the least recently active, never the most recently active one (`topicsOmitted` = number left out; absent when none); then the oldest `failed`, `confirm` and `review` cards left out (counted in `todosOmitted`). Cards in `building`, `reviewing` or `merging` are never left out; the most recently active topic is trimmed last. A trimmed snapshot carries `snapshotTrimmed: true`; the top-level flags `snapshotTrimmed`, `todosOmitted`, `topicsOmitted` and `memoriesOmitted` are optional and absent on an untrimmed snapshot, so older clients are unaffected. `counts` is computed before trimming and always describes the full board. A value between 1,500,000 and 2,000,000 bytes after every stage is still returned. Above 2,000,000 bytes the call does not fail (a write that already succeeded must not be reported as an error): it returns a contract-valid degraded snapshot with `snapshotOverflow: true` and `overflowBytes` (size of the fully trimmed board). In it `settings`, `concurrency`, `counts`, `runtime`, `schedules` and `quotaProviders` are real, `memories` is an empty array (`memoriesOmitted` gives the real number), uploaded avatars are replaced by their stand-ins, and every topic and todo is reduced to a stub with `stub: true` so the board can still list them: a topic stub keeps `id`, `title`, `archived`, `updatedAt`; a todo stub keeps `id`, `number`, `title`, `phase`, `gateOwner`, `gateKind`, `updatedAt`, `projectId`, `topicId`. All other collections on a stub are present but empty (`messages`, `queuedItems`, `brief`; `tags`, `diffs`, `buildChat`, `timeline`, `fallbackHistory`, `evidence`, `question`) so existing clients do not break on a missing field. If the base of the degraded snapshot is itself over 1,500,000 bytes, `agents` and `projects` are not emptied but reduced to stubs with `stub: true` (an agent stub keeps `id`, `name`, `role`; a project stub keeps `id`, `name`, `monogram`, `accent`; stub ids are cut to 120 characters) so the lists still point at the entry to fix, and `schedules` and `quotaProviders` are emptied; stubs are added newest first for as long as they fit, and `todosOmitted` / `topicsOmitted` count any that did not. After the stubs are added the size is checked once more against 2,000,000 bytes: if it is still over, `agents` and `projects` are emptied, and if even that is over, only `settings`, `concurrency` and `counts` are kept (each reduced to its values of at most 1,000 bytes; all other collections empty, `runtime` an empty object), so the returned value never exceeds the host limit. The UI does not show a notice for this flag yet. Saving an agent whose `avatar` equals its own default marker while an uploaded avatar is stored keeps the stored upload; `update-project` with `avatar` equal to `omitted:<projectId>` keeps the stored project avatar (an empty string still clears it).
- View-only limits applied in `get-state` before trimming, never written back: `settings.charter` over 20,000 characters (`settings.charterTrimmed`), `topics[].lastError` over 2,000 (`topics[].lastErrorTrimmed`), topic message `text` over 20,000 (`messages[].textTrimmed`), and for todos `spec` (`specTrimmed`), `plan` (`planTrimmed`), `title` (`titleTrimmed`), `buildChat` (`buildChatTrimmed`) and `lastError` (`lastErrorTrimmed`) over their storage caps. `topics[].queuedItems` carries the newest 20 queued follow-ups; `topics[].queuedItemsOmitted` is the number of older ones not included (absent when none). The queue itself is not shortened.
- Worktree retention: marking a todo done (`complete`) or closing it (`close`) removes its plugin-owned worktree when `git status --porcelain` there is empty, clears `worktreePath` and keeps the task branch, so unmerged commits survive and a later restart recreates the worktree from that branch. A worktree with uncommitted or untracked changes is kept as is. Merging, discarding and deleting keep their existing cleanup.
- Closing a todo that is `building` or `reviewing` stops its build/review session first and then lets queued todos take the freed slot.
- Memory, question, brief and queue caps, aligned with the UI RPC contract: memory `content` 4,000 and `title` 160 characters (`db.upsertMemory`; `manage_memory` declares the same `maxLength`); a todo question's `title`, `why`, `answeredText` and each option `label` 2,000 characters (`ask_user`, `db.updateTodo`); each Topic Brief text field (`goal`, `progress`, `next`, `waitingOnYou`, `waitingTitle`, `waitingRecommendation`, `blocked`) and each waiting option label 2,000 characters (`ask_user` on a topic, `update_topic_brief`, `db.updateTopic`); a queued follow-up's `text` 12,000 characters (`db.enqueueTopicItem`; an item re-queued with its own id keeps its stored text). As with the other caps, only fields the write carries are cut, and older oversized rows are shortened in `get-state` only: `memories[].contentTrimmed` / `titleTrimmed`, `todos[].questionTrimmed`, `topics[].briefTrimmed`, `queuedItems[].textTrimmed`.
- Decision options are normalised first and capped afterwards, so the capped form is what is stored: each option `label` 2,000 characters and each option `id` 120 characters, for todo questions (`ask_user`, `db.updateTodo`) and topic brief `waitingOptions` (`ask_user` on a topic, `update_topic_brief`, `db.updateTopic`); `ask_user` declares `maxLength` 120 on option `id`. An id that collides with another only because it was cut becomes its positional `opt-N`. Options stored before the cap are shortened in `get-state` only (`questionTrimmed` / `briefTrimmed`); `answer` and topic decisions accept either the full stored id or the shortened id the board shows and resolve to the same stored option.
- Values that are used as given are refused, not cut, when over their limit; the write fails with `<field> 超过 <N> 字符上限` and nothing is stored. This applies to model config strings (`id` 120, `engine` 80, `provider` 160, `model` 240, `apiMode` 60, `baseUrl` 500, `reasoningEffort` 40; both `modelConfigs[]` entries and the flat single-config fields), `settings.defaultCloneRoot` (1,000) and project `repoPath` (1,000), `githubRepo` (200), `remoteUrl` (500), `defaultBranch` (120), `testCommand` (500). Cutting a path, URL, model id or shell command would silently turn it into a different one. Descriptive text is shortened instead: model config `label` 80, project `name` 120 and `description` 2,000. The limits equal the `maxLength` already declared on the UI RPC inputs; `configure_agent`, `configure_chief` and `configure_project` now declare them too. Only a value that changes is checked, so saving an entry whose older stored value is over-long neither fails nor rewrites it.
- Rows stored before these limits are shortened in `get-state` only: `agents[].modelConfigs` and the flat config fields (`agents[].modelConfigsTrimmed: true`), `settings.defaultCloneRoot` (`settings.defaultCloneRootTrimmed: true`) and project text (`projects[].trimmedFields` lists the shortened fields). `update-project` treats a value equal to the shortened board form of an over-long stored field as "unchanged", so saving the project form from such a board keeps the full stored text; the test gate always runs the stored command.
- Saving an agent never replaces a longer stored model config string by its shortened board form: in `db.upsertAgent`, a flat config field or a `modelConfigs[]` string field (configs are matched by `id`) whose incoming value equals the shortened view of an over-long stored value keeps the stored text. A field is written only when it changes to a different value, which is then checked against its limit.
- Tags, topic titles, agent references and schedule fields: a todo keeps at most 8 tags of at most 40 characters each (`db.createTodo`, `db.updateTodo`; longer tags are shortened, and `createTodoInput.tags.items` declares `maxLength` 40); a topic `title` is stored within 160 characters (`db.createTopic`, `db.updateTopic`; `rename_topic` declares `maxLength` 160). Older rows are shortened in `get-state` only (`todos[].tagsTrimmed`, `topics[].titleTrimmed`). A project's `ownerAgentId` / `reviewerAgentId` over 120 characters, and a schedule's `runAtIso` over 80 or `agentId` over 120 characters, are refused with `<field> 超过 <N> 字符上限` and nothing is stored; `configure_project`, `create_schedule` and `update_schedule` declare the same `maxLength`. An unchanged stored value is not re-checked.
- A refused write stores nothing. `configure_chief` / `quick-configure-chief` validate the settings part and the agent part first (`db.updateSettings` and `db.upsertAgent` with `dryRun`) and only then write either, so a refused field never leaves the other half saved.
- Todo and memory id fields are used as given and refused when over 120 characters (`<field> 超过 120 字符上限`, nothing stored): `agentId`, `reviewerId`, `topicId` in `db.createTodo` (checked before a card number or a topic is created) and a new memory `id` or changed `scopeId` in `db.upsertMemory`; `create_todo` (`topic_id`, `agent_id`) and `manage_memory` (`memory_id`, `scope_id`) declare `maxLength` 120. Rows stored before the limit are shortened to 120 characters in `get-state` only, with `todos[].trimmedFields` / `memories[].trimmedFields` listing the shortened fields. A shortened memory `id` sent back by a client resolves to the stored row for update and delete, and a shortened `scopeId` sent back keeps the stored value.
- Agent ids and the Chief agent id are bounded at 120 characters. `db.upsertAgent` refuses a new agent `id` over 120 (`configure_agent` declares `maxLength` 120 on `agent_id`); `db.updateTodo` refuses a changed `agentId` / `reviewerId` over 120; `db.updateSettings` refuses a changed `chiefAgentId` over 120 before anything is written (`configure_chief` declares `maxLength` 120 on `chief_agent_id`). Rows stored before the limit are shortened in `get-state` only: `agents[].id` (with `agents[].trimmedFields` containing `id`, and the agent's `cooldowns[].agentId` shortened the same way) and `settings.chiefAgentId` (`settings.chiefAgentIdTrimmed: true`). The shortened agent id resolves to the stored row for save and delete, and a shortened `chiefAgentId`, `agentId` or `reviewerId` sent back keeps the stored value. An exact stored id passed by internal callers still addresses its row.
- An over-long id that addresses an agent row already stored (written before the limit) can still be assigned (since 0.9.22): when `db.updateTodo` writes `agentId` / `reviewerId` or `db.updateSettings` writes `chiefAgentId`, a value over 120 that is the full stored id, or its shortened board form, is written as the stored id; any other value over 120 is still refused. `start-build`, the concurrency queue and schedules resolve a shortened agent id to its stored row before picking the agent. `delete-agent` resolves the id first and compares the stored id with `settings.chiefAgentId`; when the deleted agent was the Chief, the binding moves to a remaining Chief-role agent, else to the first remaining agent, else to `''`. `clear-agent-cooldowns` resolves the shortened id before deleting the cooldown records. No stored data changes shape.
- An agent's `systemPrompt` is written (cut to 20,000 characters) only when it changes. A save that omits it, sends it back unchanged, or sends the shortened form the board shows for an older over-long prompt keeps the stored text; `get-state` shortens such a prompt in the view only (`agents[].systemPromptTrimmed: true`), and workers keep receiving the full stored prompt.
- Other stored text caps: `settings.charter` 20,000 characters (`db.updateSettings`; `configure_chief` declares the same `maxLength`), `topics.last_error` 2,000 characters (`db.updateTopic`), topic message `text` 20,000 characters (`db.addTopicMessage`). Text over a cap keeps its head and ends with `…`.
- Caps apply only to a field the write actually carries. `db.updateTodo`, `db.updateTopic` and `db.updateSettings` never shorten a field that is not in the patch, so a row written before the caps keeps its full `spec`, `plan`, `title`, `buildChat`, `lastError` or `charter` through unrelated updates (timeline entries, phase changes, renames); agents keep receiving the full stored text and only the board view is shortened.
- Stored todo text is capped in `db.updateTodo`, the only write path for these fields (`src/server/diff-budget.mjs`): `lastError` 2,000 characters; each timeline `event` 600 characters and the newest 80 entries; `plan` 50,000 UTF-8 bytes; `buildChat` the newest 24 entries, each `text` 4,000 characters. `spec` 20,000 characters and `title` 200 characters, applied in both `db.createTodo` and `db.updateTodo`; the MCP tools `create_todo` / `update_todo` declare the same `maxLength` (the UI RPC `create-todo` keeps its stricter 12,000-character `spec` limit). A `spec` over the cap keeps its head, so a `User Decision` line appended by `answer_question` to an already full spec is cut; the answer still reaches the worker in the resume message and stays in the timeline. Text over a cap keeps its head and ends with `…`; when a `lastError`, timeline event or `spec` is cut, one host log line (`log.warn`) records `todoId`, the original `length` and `head` (its first 2,000 characters), never the whole text; a log sink that throws does not fail the write. No schema or version change: existing rows are not migrated, a field is brought within its cap only when a later write carries that field, and until then `get-state` shortens an oversized stored `lastError` in the returned value only and marks it `todos[].lastErrorTrimmed: true`. The same applies to an oversized stored `spec` (`todos[].specTrimmed: true`); workers still receive the full stored text.
- Session Trace (`get-session-trace`) reads `ctx.host.sessions.get/messages` only for sessions recorded on this profile's topics (`chief_session_id`) or todos (`build_session_id`, `review_session_id`); tool calls are paired with results by `tool_call_id`, long payloads are clipped server-side, and nothing is persisted.
- Chief busy-poll guard: a Chief shell tool call with `sleep >= 20s` or a direct read of `ekko-todo.sqlite` / plugin-data is warned once per turn and stopped on the second occurrence; unfinished todos of the topic are auto-watched so the Chief is woken on change.
- Chief loop guard: within one Chief turn, the same sentence (>= 4 characters, whitespace ignored) written 3 times in a row with no real tool call in between (6 times in a row regardless), or 5 `tool_describe` calls in a row with no real tool call in between (`tool_search` is not a real call), stops the host run. The topic gets `isRunning=false` / `activeRunId=''` and one `kind: "system"` message whose `text` and `progressNotice` start with `检测到重复输出，已中止本轮`; queued topic messages are then drained. Late tool events of the stopped run are ignored until that session reports a run start or end. No contract field is added; the limits live in `src/shared/loop-guard.mjs` (`REPEAT_NARRATION_LIMIT`, `REPEAT_NARRATION_HARD_LIMIT`, `DESCRIBE_ONLY_LIMIT`, `MIN_NARRATION_CHARS`) and are not configurable. The client applies the same rule to the live stream and shows `检测到重复输出，正在中止本轮…` until the stored message arrives.
- `read-local-file` (read-only) serves host files to the chat preview: `mode` meta | text (first 400 KB) | bytes (base64, ≤1,000,000 bytes per chunk from `offset`, `eof` marks the end). It resolves symlinks, refuses credential/secret/database files and paths outside the allowed roots (`src/server/local-file.mjs`), and caps files at 60 MB. The client (`src/client/local-files.js`) caches Blob URLs, limits reads to two in flight and never puts a host path into an `<img src>`.
